# 开发流程

本页说明 ProjectWiki 的开发步骤，以及路线图、计划、决策和知识正文如何配合。接入项目可以按规模采用同样分工。

架构决策记录（Architecture Decision Record，ADR）说明重要选择的依据；plan 是一项工作的执行计划；roadmap 是项目的路线图。

## 文件职责

| 文件 | 回答的问题 | 不应重复的内容 |
|---|---|---|
| roadmap | 接下来做什么，先后顺序与依赖是什么 | 不复制计划步骤和执行流水 |
| plan | 这项工作怎样完成、验收与交接 | 不复制需求和设计全文 |
| ADR | 为什么在多个方案之间作出这个重要选择 | 不承担待办列表与进度看板 |
| 当前知识 | 今天适用的需求、原则、设计和规范是什么 | 不堆积开发日志 |

第一版路线图使用单个 `dev/roadmap.md`。一项工作使用一份 `dev/plans/<主题>.md`，步骤、进度、阻塞与验证在这里更新。只有真实需要跨计划汇总时才建立状态页，不预设独立并行看板。

## 开始工作

先找到目标需求或维护目标，核对适用规则、当前设计和影响范围。新建计划前检查已有计划及对应历史。

局部修复可以引用现有任务或提交记录，保留修改依据与验证结果。涉及多步骤协作、风险边界、交接或长时间工作时，建立计划。不要按修改行数机械判断风险。

计划至少包含目标、关联知识、实施步骤、验收、未决事项和验证记录。进度只维护在这份计划里，路线图通过链接引用它。

当前知识中的工作导航优先链接 `dev/INDEX.md` 或 roadmap 等长期入口，减少计划归档时的改链。需要追踪具体差距或引用验证依据时，可以直接链接计划，并写明用途；归档时按引用关系定向修复。

## 重要取舍与 ADR

当选择会持续影响结构、接口、依赖或兼容性，并且存在需要解释的替代方案时，创建 ADR。还未确定的取舍可以先记在计划中。

ADR 使用背景、替代方案、决定和后果四部分。只影响模块的记录放到模块 `docs/decisions/`，跨模块记录放到根 `docs/decisions/`。使用描述性文件名，避免依赖全局顺序编号。

ADR 不作为所有任务开工前的固定手续。已采用的决定可能长期有效，不因对应计划完成而归档。当前设计页保持现行结论，需要解释取舍时链接 ADR。

## 决定或设计变化时同步文档

读者和 Agent 按当前需求、原则和设计工作，ADR 只解释原因。所以决定或设计发生变化时，在同一次改动中更新所有仍然描述旧结论的现行文档。不能只改 ADR、只改代码，或者把同步留到以后。

| 发生了什么 | 同一次改动中要做的事 |
|---|---|
| 采用一份新 ADR | 按新结论修改受影响的需求、原则、设计和模块入口；`AGENTS.md` 里复述了该规则的条目一起改；需要解释原因的设计页链接到这份 ADR |
| 一份 ADR 被替代 | 新 ADR 写明替代了哪一份以及原因；旧 ADR 只把状态改为"被替代"并链接新 ADR，不改写当时的理由；现行文档中指向旧 ADR 的链接改指新 ADR |
| 一份 ADR 被废止，没有替代 | 旧 ADR 状态改为"废止"并写明原因；现行文档删除依赖这项决定的内容，或改写成现在的做法 |
| 设计改变，推翻了某份已采用 ADR 的结论 | 补一份新 ADR 替代它，然后按上一行处理。不能让设计页和 ADR 都标为当前、内容却互相矛盾 |
| 设计改变，但不涉及任何已采用的决定 | 原位修改设计页即可，不需要新建 ADR |
| 代码行为改变了文档描述的接口或规则 | 和代码一起提交对应的需求、设计或模块 README 修改 |

已经结束的计划和归档文件记录的是当时的情况，不随新决定改写。被替代的 ADR 不再有现行文档引用后，可以按[生命周期规则](../docs/design/lifecycle.md)归档。

**找出受影响的文档。** 只查链接会漏掉直接复述结论的地方。两种方法要一起用：

1. 查链接到这份 ADR 的现行文档。可以用 `rg -l '<ADR 文件名>'`，普通 `rg` 默认不搜 `archive/`，正好只得到现行文档。也可以运行 `python3 scripts/wiki/wiki.py archive <ADR 路径> --root .`，用它的只读预览列出所有入链，不需要真的归档。
2. 按这项决定的关键词搜索现行文档，找出没有链接、但直接写了旧结论的地方，尤其是 `AGENTS.md`、需求页和模块 README。

以 `demo/` 为例：查链接能找到引用 [字符计数决策](../demo/notes/docs/decisions/unicode-length.md) 的 4 篇现行文档；但 `demo/AGENTS.md`、`demo/docs/requirements.md` 和 `demo/notes/docs/requirements.md` 直接写了"按 Unicode 码点计数"，却没有链接这份 ADR，只有按关键词搜"码点"才能找到。如果计数规则改变，这 7 处都要在同一次改动中更新。

检查工具只能确认链接存在、路径有效，不能判断文档内容和新结论是否一致。这一步需要提交者通读改动范围，评审时也要核对。

**提交时的提醒。** 配置了 `remind` 的项目，每次提交都会由 Git 钩子检查：
- 改了代码却没改对应文档，会给出提醒；
- 改了决策记录，会列出还链接着它、但本次没有改动的文档；
- 改了需求、原则或决策，会提醒先向用户确认；
- 某组代码累计改动过多、文档一直没有复核，会先提醒，超过上限后拦截。

确实复核过、文档不用改时，在提交信息最后一段写 `Docs-Reviewed: <名称> <理由>`。机制和配置见[自动化设计](../docs/design/automation.md#提交时的文档提醒)。

## 实施与验证

按计划推进，步骤完成与验收结果只更新计划。发生设计变化时原位更新知识；里程碑变化时只调整路线图中相应入口。操作指南中的读者检查清单与项目进度不同，不能仅凭 checkbox 语法判定违规。

交接时写清完成与剩余事项、源码或配置快照、验证命令与结果、已知失败，以及哪些改动已经集成。接手者核对相关差异后决定重验范围。

## 完成与归档

完成或取消工作时，核对验收与剩余事项的去向；把新增或改变的稳定知识写回 `docs/`。没有知识变化时不新增空文档。

归档结束的计划及其附属证据，保持原相对路径。路线图只更新相应链接。仍有效的需求、原则、设计与 ADR 保留原位，具体规则见[生命周期与归档](../docs/design/lifecycle.md)。
