# Project development constraints

- `docs/` holds the current requirements, principles, and design; `dev/` holds candidate proposals, tasks, and progress; `archive/` holds history. Search the history as the task requires, and do not take historical text directly as the current specification.

- Implementation constraints such as control sizes and call order go in the module documents and are not piled into this file.
- The documentation development workflow follows `scripts/wiki/en/workflow.md` by default; an existing workflow does not automatically take precedence, and the two sets of requirements are not applied on top of each other by default. For duplicates or conflicts, migrate the original entry and its readers as described under "Shared workflow and project adaptation" there; before the migration, do not silently bypass a strong constraint or a hook that is currently in force.
- Stable knowledge is written for human readers: state the specific object, the conditions of application, and the behavior, and avoid AI boilerplate, translationese, and unexplained internal abbreviations.
- The path of a new document must not contain a space, `#`, `%`, or parentheses; after copying a template, rename it to a specific topic. The other naming advice and the use of `check-new` are in `scripts/wiki/en/README.md`.
- Archive a whole page to the `<main archive root>/<original relative path>` chosen by the configuration (in this template the main root is `archive/` by default), keeping the file name and the directory; when the target already exists, stop and do not overwrite it. Preview with `python3 scripts/wiki/wiki.py archive <path> --root .`, then add `--apply --expect <plan_sha256>` to apply; do not move files or change links by hand. Before creating a document, check the matching history; on a hit, decide between restoring it, continuing it, and starting a new topic, and do not treat a same-named file in history as a permanent ban on the name.
- When a module is involved, first read that module's entry and the contracts that apply, then check the implementation and the way to verify.
- [TODO: registers that keep growing, for example `dev/progress/deferred-gaps.md`] are searched by ID or keyword, and only the matching lines are read; do not load the whole file.
- The formats of status lines, verification lines, requirement entries, review findings, and inbox items, and the way requirement IDs and review route numbers are assigned, are governed by `scripts/wiki/en/formats.md`; configuration and rule names are searched by name in `scripts/wiki/en/reference.md`, which is not read as a whole.
- The development workflow rules (the order from requirement to verification, which documents to update when a decision or a design changes, where troubleshooting experience is written, how the work of a review is divided, and when to archive) are governed by `scripts/wiki/en/workflow.md`; read them there, and do not copy them into this file. This file keeps only the hard rules that directly cause errors when ignored.
- Checkers, authors, owners, and signers are written as `human:<name>` or `agent:<name>`. An agent may write itself only as `agent:` and never as `human:`; once `remind` is configured and the hooks are installed, a `human:` name added in a commit produces a `[user]` reminder. After checking a knowledge page, write `Verified: agent:<name>, YYYY-MM-DD.` below the title, and on a page that goes out of date also write `Review by: YYYY-MM-DD.`
- A formal review goes in a specific directory that matches the `reviews` configuration, by default `dev/reviews/<start date>-<topic>/` in this template, with one file for each route and one section for each finding; verification, plans, and sign-offs are written in the section of the finding, and a second check appends a row to the verification table without creating a file. The checker must not be the author. Route numbers are assigned by the person who consolidates the review. What can be written as a section of an existing file does not get a new file.
- Plans, reports, research, and drafts generated by AI tools or skills go in `dev/` and must not be written into `docs/`; when a tool writes to `docs/` by default, change its configuration first, or move the output away after it is generated.
- When you find a problem or have an idea but are unsure where it belongs or whether to act on it, use the inbox source declared in the development entry, and link tasks and close items by the rules of that source. When nothing else is declared, write one file for each item at `dev/inbox/<type>/<topic>.md`, recording at least the status, the source, the observation or need, the basis of verification, and the disposition; do not change `docs/` directly, and do not create ad hoc directories. When an item in the repository has been handled, write where it went, change the status to `finished`, and then archive it with `archive`.
- Stage only the files related to the current work, and do not revert or clean up the uncommitted changes of other people or other agents. When merging, do a three-way merge of the files that both sides have changed, and do not take one side wholesale by default.
- When leaving a placeholder implementation or a `TODO`, state the reason, the impact, and when it will be cleaned up; for a known failure, state its exit condition. "It was already red before the change" is not a reason to leave it unhandled indefinitely.
- Run `python3 scripts/wiki/wiki.py verify --root .` according to the scope of the change. Commands and the directories they run in are registered only in `verify` of `docs/wiki.json`, and any command with a nonzero exit code is a failure; the template registers only the document check, so add the project's own test and build commands at adoption. The verification record of a plan is generated from the output of `verify`; command results are not written by hand.
- Steps that a tool can carry out exactly are left to the tool; verification lines, the renewal of review-by dates, human sign-offs, and requirement statuses are written by a person or an agent after judging, and the tool does not write them on anyone's behalf.
- When current knowledge changes, update the matching text in place; Git keeps the history of ordinary revisions. Do not mechanically create a plan or rewrite a status page with every commit.
- For a new feature or a change in behavior, write or modify the requirement entry in the same change, and tests write the acceptance IDs in their descriptive text. When the boundary is clear, no multi-step collaboration or handoff is needed, and there is no significant risk or contract change, the requirement entry and the tests are enough, without a separate design or plan; an existing design that has become untrue must still be updated. When a design or a plan is needed, each cites the requirement on a `Requirements:` line. Acceptance items that can be tested get tests; only what no command can prove is marked `(manual)` and gets an acceptance check record. An ordinary fix does not create a requirement; citing the existing ID is enough. The division of work is in the [development standards](docs/standards/development.md).
- When a decision record is adopted, superseded, or retired, or when a design or the behavior of an interface changes, update in the same change the requirements, the design, the module entries, and the items of this file that still describe the old conclusion. Find the affected documents in two ways, by links and by keywords. A design change that overturns an adopted decision needs a new decision record.
- Run `python3 scripts/wiki/wiki.py remind --root .` when starting a task. The Git hooks also print reminders at commit time. A single `docs-not-updated` is an `[info]` notice and, below the accumulated threshold, does not require a review or a trailer; text known to be untrue must still be updated in the same change. On an `[agent]` reminder of an accumulated review, check and then update the documents, or write `Docs-Reviewed: <name> <reason>` in the last paragraph of the commit message; handle other `[agent]` reminders as the message says. On a `[user]` reminder, confirm with the user first, unless the user has already asked for the change, and report it in your summary. The thresholds and the ways of handling are under "Documentation reminders at commit time" in `scripts/wiki/en/reference.md`. Hooks must not be skipped with `--no-verify`.
- Everyday wiki searches exclude the root `archive/` through `.ignore`. When history is needed, search it specifically; `grep -R` does not read `.ignore`, so add `--exclude-dir=archive` to routine queries.
