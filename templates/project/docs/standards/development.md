# 开发规范

范围：【待填：适用范围】。状态：当前有效。

## 修改与验证

【待填：编码、兼容性、测试、构建、集成与发布的实际要求。】

修改前明确目标、适用约束、实现入口和验证方式。小范围修复可复用已有任务或提交记录；新需求、契约变化、数据与权限边界变化需要相应需求和设计审查。

按改动范围选择验证命令。命令和运行目录只登记在 `docs/wiki.json` 的 `verify` 字段，任一命令退出码不为 0 就是失败；本页说明每类改动要求哪些命令通过，不复制命令清单。模板只登记了文档检查 `check`，接入时补上项目自己的测试和构建命令。统一运行入口是：

```bash
python3 scripts/wiki/wiki.py verify --root .
```

| 改动范围 | 通过条件 |
|---|---|
| 【待填：例如某个模块的源码】 | 【待填：对应 `verify` 命令退出码为 0】 |
| 只改文档 | `verify` 输出中对应的 `check` 通过 |

已知失败要写明失败的测试或命令、复现方式和退出条件。"改动前就是红的"不能作为一直不处理的理由；暂不处理时登记到对应计划或 `dev/inbox/`。

留下占位实现、空分支或 `TODO` 时，写明原因、影响的行为，以及什么时候由哪项工作清理。

## 协作

只暂存本次工作相关的文件。不要为了得到干净的工作区而还原、清理或暂存其他人和其他 Agent 的未提交改动。

合并或变基时，两边都改过的文件做真正的三方合并，不默认整份采用一边。

## 文档与工作记录

当前知识原位维护，普通修订历史交给 Git。整篇不再承担当前职责时才考虑归档；计划、任务和原始验证材料结束后可归档，仍有效结论留在当前知识中。

路线图维护方向、先后与里程碑，引用具体计划；计划维护实施步骤、验收和任务进度；重要取舍写决策记录。三处不重复抄执行流水。

用户能感知的变化写进 `CHANGELOG.md`，按版本分段。它是给用户看的稳定记录，只写行为变化和升级注意事项，不写开发过程。

验证记录写明可取回的源码或变更快照、命令、结果和已知失败。命令和结果用统一的 `verify` 入口生成，命令清单只登记在 `docs/wiki.json` 的 `verify` 里。记录只证明对应验证对象，不自动代表当前主分支。

## 写作

直接写对象、规则、依据和适用范围。区分事实、推测与待办。避免空泛评价、内部简称、翻译腔，以及未经执行的通过结论。
