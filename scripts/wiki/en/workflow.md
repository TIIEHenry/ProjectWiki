# Development workflow rules

> English translation of [开发流程规则](../workflow.md). The Chinese page is authoritative: if the two differ, the Chinese page applies.

This page holds the workflow rules that agents in an adopting project follow during development. What the tool can catch (links, status lines, the format of requirement IDs) is checked by `check` and `remind`. What the tool cannot catch is written here: when to write a decision record, which documents to update when a decision changes, how the work of a review is divided, and what should be archived. The `AGENTS.md` of an adopting project links to this page and does not copy passages from it.

Look up commands in [README.md](README.md), and configuration fields and rule names in [reference.md](reference.md) (search by name; do not read the whole page). The fixed formats the tool reads, namely status lines, verification lines, requirement entries, review findings, and inbox items, are in [formats.md](formats.md). The workflow rules are on this page.

A decision record (Architecture Decision Record, ADR) explains why an important choice holds. A plan is the steps for carrying out one piece of work. A roadmap is the direction of the project and the order of its work.

## Shared workflow and project adaptation

After adoption, this page governs the project's documentation workflow, and the project's `AGENTS.md` and development entry point here. When adoption or an upgrade changes the workflow, go through the project's existing requirements against this page: delete or replace the duplicated or conflicting items in their original entry, and update the checkers and other readers that depend on those items. That an old rule already exists, or is stricter, is not a reason to keep it; the two sets of requirements must not be applied on top of each other by default.

Add a project rule or declare an exception only when the project has a real need that the shared workflow does not cover. Write it in the entry where the project's rules already live: name the shared rule it relates to, the specific condition that triggers it, and the reason it is necessary. Where an authoritative text already exists, link to it; do not build a separate list of exceptions, and do not require each task to state the exception again. Cancel the exception when its condition no longer holds. An old requirement without such grounds is to be cleaned up during adoption; it does not count as a valid exception merely because nobody has dealt with it yet.

Business, interface, and security constraints are not deleted because the documentation workflow is being unified. For the records an execution suite uses for dispatch, recovery, and concurrency control, check what actually reads them, as described in [Task records and status pages](#task-records-and-status-pages); before changing a protocol, migrate its readers and verify the result. Keeping a necessary use does not mean keeping duplicate records, nor does it make every step of the suite an automatic exception to the documentation workflow.

When an everyday task runs into a conflict that has not been cleaned up, treat it as a gap in the adoption and point out the conflicting items and the operations they affect. If the current authorization includes changing the workflow, revise the original entry and the readers involved, then follow the shared workflow. If it does not, continue with the work that is free of conflict, and report which part is blocked and what the adoption still lacks. Do not ignore a current explicit instruction or bypass the hooks on your own, do not apply both workflows together as a stopgap to finish the task, and do not declare that the old rule takes precedence from now on.

Directories, numbering, and registered status wording are adaptations made through the project's configuration; they are not exceptions to the workflow. The directory examples on this page are for a new project that has no layout yet. The actual locations are the ones given by the project's entries and registered in `docs/wiki.json`; the fields are in [Configuration and rules](reference.md). Reuse the existing locations and do not create a second set of directories because the example paths differ. When the configuration is missing something or conflicts, complete the registration first.

## The order from requirement to verification

New features and changes in behavior proceed in the order requirement, implementation and tests, verification; design and plans are added according to the extent of the impact. A local fix that does not change an existing requirement does not add a requirement entry; citing the related IDs in the existing plan or in the commit is enough. If the fix reveals a gap in the requirement itself, go back to step 1.

1. Add or change an entry in the requirements file, write acceptance criteria that can be checked, and set the status to `proposed`. Take the ID as described under how IDs are assigned in [formats.md](formats.md#how-ids-are-assigned); when parallel branches take the same ID, the side that merges later changes its ID.
2. Once the boundary of the requirement and its acceptance criteria are clear, change the status to `accepted`. When a change in structure, interfaces, dependencies, or compatibility needs explaining, update the related design and cite the requirement with `Requirements: <ID>`.
3. Create a plan when the work involves collaboration over several steps, significant risk, a handoff, or a long duration. The plan begins with `Requirements: <ID>`, and each step states which acceptance IDs it satisfies. When the boundary is clear, there is no significant risk or contract change, and neither multi-step collaboration nor a handoff is needed, the requirement entry and the tests are enough for tracing; existing text that has become untrue must still be updated.
4. During implementation, tests write the acceptance IDs in their descriptive text. When the implementation is complete, change the status of the requirement to `implemented`.
5. After the tests have run or the manual check is done, add an `Evidence:` link to the requirement entry. An acceptance item marked `(manual)` also gets an acceptance check line. Then change the status to `verified`. An acceptance item that can be tested gets a test; a check record does not stand in for it.

Design documents that exist and plans write `Requirements:` lines, and tests write acceptance IDs, so the IDs tie the related records together. `check` reports references to IDs that do not exist and acceptance criteria that no test refers to; it does not require a new document because a design or a plan is missing. The format of an entry is under requirement entries in [formats.md](formats.md#requirement-entries).

## Task records and status pages

The steps, the progress, and the verification of a task each have exactly one authoritative record; reuse an existing plan or task record where possible. An ordinary fix can keep its reasoning and verification result in the commit message alone, and no new plan is required. Do not update a status page mechanically with every commit, and do not leave a running log of past events in the current overview. When cleaning up an existing overview, first delete duplicate records and cut down the content and the number of updates; splitting it into more files is not a required step.

First tell coordination summaries apart from execution protocol records, by who actually reads them and for what. Records that a scheduling agent or program uses for dispatch, recovery, concurrency control, handoff, or acceptance tracing are kept as the contract of the execution suite requires; a status, queue, or slot register maintained by hand may serve these purposes too. Each fact is still maintained in one place only, and other pages link to the original record or show a view generated by a tool. A file must not be deleted wholesale, or exempted wholesale, because its name contains `status`, because it is a board, or because its directory is called `loop`. The short status page described below is a coordination summary and does not replace execution protocol records.

Before changing the path, the fields, the update trigger, or the way of retiring an existing record, check who reads it, migrate those readers at the same time, and verify. Fixed entries and existing mappings that the suite depends on can stay. Whether to split a record by module also depends on its actual readers; do not break a path the suite reads merely to reduce the number of documents. The current overview and the historical log should still be kept apart, and evidence that is still used for recovery or acceptance is not moved away just because the task has ended.

Create or keep one short status page (such as an existing `status.md`) only when there is a real need for project-wide coordination that the existing plans, task records, and module READMEs cannot meet. It holds only links to the current tasks, cross-module dependencies, and open questions. Task details stay in their original records, and the page is updated only when this coordination information changes. When the need for coordination is gone, merge the links that are still useful back into the development entry and retire the status page. Complete process records that have ended are handled by the archiving rules, and Git keeps the rest of the revision history.

Consider module status pages only when several modules advance independently over a long period, when readers care about one part only over a long period, or when several people editing the overview keep running into conflicts. Only a local coordination purpose that the existing plans and the module README cannot meet justifies a separate page. Follow the project's existing module identifiers and naming rules, do not create one for every module by default, and do not add path or mapping configuration for the sake of the split. A module status page likewise maintains coordination information only and does not copy task progress.

## Sharing the development entry with an execution suite

ProjectWiki maintains current knowledge, the tracing between requirements and records, document checks, and archiving. An execution suite maintains dispatch, the execution state of tasks, concurrency conflicts and slots, recovery, and closing out. Local process IDs, locks, caches, and logs are managed in the suite's runtime directory and are not copied into knowledge pages.

When a project uses both, register the project binding in the existing development entry that the root `AGENTS.md` points to. A new project uses `dev/INDEX.md` by default; an existing entry does not have to be renamed. The binding is a description, for people and agents to read, of the roles and their actual sources. It is not a new field in `docs/wiki.json`, and it is not another task list. Describe the following, as far as the suite actually needs to read them:

| Role | What the entry states |
|---|---|
| Task source | Which plan, requirement, issue, or submitted task the work is taken from; which ID or link identifies the original task |
| Execution and coordination records | Who maintains dispatch, execution state, conflict scope, slots, and the basis for recovery, and where they are actually recorded; where the entry to the suite's rules is |
| Inbox source | Which existing inbox or issue system newly found problems go into; how existing items are tied to the original task |
| Verification entry | Where the project's verification is run from, and where its results and limitations are kept |
| Archiving convention | Which records are archived when they end, and where; when the readers used for recovery or acceptance stop depending on the original location |

An old project that has not registered a binding works by its existing suite contract; once a binding is adopted, the declared actual sources govern. Register only the sources actually in use, and write `none` or `not used` explicitly for a role that is not; do not create empty files in order to fill in the table. Paths, numbering, and the meaning of statuses follow the project's existing structure and configuration; how a fixed format is read is defined by whoever provides it. A consumer reads the binding in the entry first and then finds the original record as declared; after accepting the binding it must not still insist on reading another set of default paths. When the suite cannot read an existing source, adjust the consumer first or choose an existing mapping that works; do not claim that the adaptation is done.

One record is responsible for each fact. A plan can hold the implementation steps, the suite's task record holds dispatch and execution state, and the slot register holds what is currently occupied; the three serve different purposes and can coexist. Tie them together with the ID or link of the original task; a summary only links or is generated. The lifecycle status of a plan and the scheduling state of a suite task are interpreted separately and do not override each other. That a task has finished executing does not by itself mean that the requirement is verified, that the plan can be archived, or that the slot has been released. Each end condition is checked according to its own responsibility; the steps needed can be done in one operation, and writing two completion records is not required.

During adoption, choose one real task and follow the binding through taking the task, dispatching or resuming it, verifying, ending, and archiving. Check that the original task can be found, that execution state and occupied scope each have one place where they are updated, that unfinished items have somewhere to go, and that the evidence can still be found after archiving. When the suite has not actually been run, report only that the binding or the document checks were verified; do not report that dispatch, recovery, or concurrent execution has passed. The suite's own phases, commands, and recovery rules are maintained in the suite's adoption instructions and are not repeated here.

## Updating documents when a decision or design changes

Readers and agents work from the current requirements, principles, and design; an ADR only explains the reasons. So when a decision or a design changes, update in the same change every current document that still describes the old conclusion. Do not change only the ADR or only the code, and do not leave the update for later.

| What happened | What to do in the same change |
|---|---|
| A new ADR is adopted | Change the affected requirements, principles, design, and module entries to the new conclusion; change the items in `AGENTS.md` that restate the rule at the same time; link the design pages that need to explain the reason to this ADR |
| An ADR is superseded | The new ADR states which one it replaces and why. In the old ADR, only change the status to `superseded` and link to the new ADR; do not rewrite the reasoning of the time. Links in current documents that point to the old ADR are changed to point to the new one |
| An ADR is retired without a replacement | Change the status of the old ADR to `retired` and state the reason; in current documents, delete the content that depends on the decision or rewrite it to describe the present practice |
| A design change overturns the conclusion of an adopted ADR | First write a new ADR to replace it, then proceed as in the superseded row. A design page and an ADR must not both be marked current while contradicting each other |
| A design changes without touching any adopted decision | Edit the design page in place; no new ADR is needed |
| The behavior of the code changes an interface or rule that the documents describe | Commit the matching change to the requirements, design, or module README together with the code |

Finished plans and archived files record the situation at the time and are not rewritten for new decisions.

**Finding the affected documents takes two passes; searching links alone misses the places that restate the conclusion directly.**

1. Links: find the places in current documents that link to this ADR. First check that `.ignore` excludes the history roots the project has registered, then search the current documents with `rg '<ADR file name>'`. You can also use the read-only preview of `archive <ADR path>` to see the inbound links the tool recognizes, without actually archiving.
2. Keywords: search the current documents for the keywords of the decision, to find the places that have no link but state the old conclusion directly, especially `AGENTS.md`, requirement pages, and module READMEs.

The tool can only confirm that links exist and paths are valid; it cannot judge whether the content agrees with the new conclusion. So the committer reads through the whole scope of the change, and the reviewer checks it too.

**When to write an ADR.** Write an ADR when a choice will keep affecting structure, interfaces, dependencies, or compatibility, and there are alternatives that need explaining. Use four parts: context, alternatives, decision, and consequences. A trade-off that is not settled yet is noted in an existing task or plan first. Use the project's existing entry for decisions; where there is no layout yet, a decision that affects a single module goes in the module's `docs/decisions/`, and a cross-module decision goes in the root `docs/decisions/`. A new project uses file names that describe the topic and does not rely on a global sequence number; existing numbers are kept. An ADR is not a fixed formality before every piece of work starts. An adopted decision can stay in effect for a long time and is not archived because its plan is finished.

## Capturing experience

Experience means the conclusions reached in troubleshooting, development, or investigation: current behavior, diagnostic methods, practices that work, and lessons from failures that hold under certain conditions. When the user asks for experience to be captured, or authorized work produces a new conclusion, first check it against the code, the configuration, the tests, or reliable sources. A conclusion that cannot be confirmed, or that conflicts with the current text, goes into the project's existing inbox source or the related task, with a note of what evidence is still missing; one that turns out on checking to be unrelated to the project's behavior is only mentioned in the report. Confirmed current behavior, external conditions, and accepted decisions are written down without further filtering, in the place the table below gives. Diagnostic methods and practices are filtered by two criteria: either another person or agent can follow them directly in a task of the same kind, or they are a method or criterion whose mechanism and conditions can be stated and which applies to problems of the same kind once the specific parameters are replaced. Those that do not qualify stay in the original task or the commit record. Without a new conclusion there is nothing to summarize, and no fixed step is added to every task or commit.

Confirmed experience is written in one of three ways. Current behavior, tool limitations, and externally imposed conditions such as security and compliance are facts: write them with their evidence into the design page or module entry responsible for the topic, and for an externally imposed condition also state its source and the consequence of violating it. A practice supported by the text of a project rule is a constraint. Rule text means requirements, principles, standards, design, and decision records, together with local code comments that the existing rules permit; a restatement in `AGENTS.md` counts as well. When a guide touches a constraint, it links to the original text and does not write a second copy. Every other practice is a recommendation: state the conditions under which it applies, and do not word it as an unconditional "must" or "must not"; readers weigh it by its conditions. To raise a recommendation to a constraint, go through the project's existing requirement, design, or decision process.

First search the existing knowledge, the tasks, and where necessary the history by symptom, scenario, and related symbols to see whether the conclusion has been recorded before, then choose where it goes:

| Content | Where it goes |
|---|---|
| Current behavior, interface details, tool limitations, and externally imposed conditions that are not yet documented | The design page or module entry responsible for the topic |
| Reusable diagnostic steps, practices that work, lessons from failures that hold under certain conditions | An existing operations guide or troubleshooting guide, or the maintenance section of the module overview ("Maintenance and practices" in the templates) |
| Constraints supported by rule text | The requirement, standard, or design responsible for the topic, distinguishing the goal from the current implementation |
| Long-term trade-offs whose important alternatives need explaining | A decision record, under the [conditions for an ADR](#updating-documents-when-a-decision-or-design-changes) |
| Observations still to be verified, hypotheses, conflicting evidence | The project's existing inbox source or the related task |
| The course and result of a single task and nothing more | The original task or the commit record |

The text states four things: the scenario it applies to; the practice, with the expected result or the way to verify it; the basis, with links to code, tests, sources, or the original task; and the known limitations or the conditions under which it does not apply. When generalizing, write out the mechanism and the necessary conditions that produce the result, and mark which specific parameters can be replaced. Keep verified cases apart from the range inferred from the mechanism, and do not write an unverified extension as a fact. When finished, ask yourself: in another task of the same kind, could the reader tell when to use this, what to replace, and how to check the result? Add it as a section of an existing page, and link to it by symptom from the navigation of the related module or task. When no page fits, add a maintenance section to the module entry or overview; whether it deserves a page of its own is decided under [Keeping the number of documents down](#keeping-the-number-of-documents-down). Do not create experience pages by event or by date, and do not create a separate experience directory or index.

Writing back stays within the files the current task is allowed to modify; a read-only task only proposes in its report where the text should go. For experience written back without the user having asked for it, the task report lists each location so that the user can confirm or withdraw it. Experience is revised, narrowed, or withdrawn in place as new evidence arrives; when a whole page has lost its use, handle it under [Lifecycle and archiving](#lifecycle-and-archiving). Content that goes out of date uses the [verification line and review-by date](formats.md#verification-line-and-review-by-date). The steps are in the [knowledge capture skill](skills/capture-knowledge/SKILL.md).

## Reviews

Checking the documents for a named page or topic reports, by default, its basis, the problems found, and the scope left unchecked in the conversation, and creates no review directory. Use the recorded process below when the user asks for a formal review, or when findings clearly need to be tracked over time, verified independently, and signed off. A single read-through does not count as independent verification or as a sign-off.

A review looks for problems systematically. A person can start it, and several agents can carry it out in parallel. The directory structure and the format of a finding are under review findings in [formats.md](formats.md#review-findings).

1. **Prepare.** Under the project's existing entry for reviews, choose a directory that matches the `reviews` configuration; a new project uses `dev/reviews/<start date>-<topic>/README.md` by default, and the directory is described under [Review findings](formats.md#review-findings). In the README, write the questions to be answered, the scope, the baseline commit, and how the review is split into routes. The person who consolidates the review assigns a route number to each route in the route table; a route added midway also has its number registered before its reviewer starts writing. Because one person assigns all the route numbers, reviewers working in parallel cannot take the same number.
2. **Find.** Each route writes only its own route file, one section for each finding, with the status `pending`. When different routes find the same problem, the one found later is judged `duplicate` at verification.
3. **Verify.** A person or agent who is not the author opens the code and documents concerned, judges the findings one by one, appends a row to the verification table in the finding's section, and then changes the status line. A finding judged `known` links to the existing plan, gap, or decision and is not handled again. The verification groups are written in the README, and the routes assigned to the groups do not overlap.
4. **Plan and sign off.** Write a plan for each confirmed or narrowed finding, in the finding's section; for a fix that spans several findings, create `plan-<topic>.md` in the same directory. The sign-off is written in the finding's section and in the summary table of the README; only the consolidator updates the summary table.
5. **Implement and close.** After sign-off the plan is the plan of execution; do not create a board that records the progress a second time. The conflict scope and slot registers that an execution suite needs are kept for their [execution protocol purposes](#task-records-and-status-pages). Conclusions that still hold are written back into the design, the requirements, or a decision; the status of the README is changed to `finished`; and the whole directory is then archived with `archive`.

**The checker must not be the author.** A re-check, a different person, or a different model each appends a row to the verification table; none of them creates a new file. The number of files in a review is roughly the number of routes plus one: rounds, models, and dates go into the table, not into file names. What fits as a section of an existing route file does not get a new file. A later review of the same topic gets a new dated directory and links to the previous review in its README; it is not appended to the old directory.

## Lifecycle and archiving

Current knowledge is maintained in place: requirements, principles, module structure, and current interface contracts keep being updated where they are, Git keeps the history of ordinary revisions, and a page is not archived as a whole because of one change or one finished task.

The history root the project registers (`archive/` by default in a new project) mainly keeps development process material that has ended. End and archive material at the following points:

- **Plans.** Archive a plan after its status becomes finished or cancelled. Before archiving, make the status line and the step list agree: if the status is finished but steps remain unchecked, give each remaining step somewhere to go (a new plan, a write-back into current knowledge, or an explicit cancellation); if every step is done but the plan is still marked active, change it to finished. The tool reads only the status line and cannot detect this kind of mismatch.
- **Inbox items.** After triage an item must be closed in some way: which plan it became, which knowledge page it was written into, which item it duplicates, or why nothing will be done. Write the outcome into the item, change the status to `finished`, and archive it. It is archived and not deleted because the reason for doing nothing will be asked about again.
- **Review directories.** After the status of the README is changed to `finished` and every plan has been implemented or handed over elsewhere, archive the whole directory in one operation. As long as one plan has not ended, the whole directory stays where it is; it is not split up for archiving.
- **Experiment reports and raw verification records.** They can be archived when the work ends; reusable conclusions are worked into current knowledge.
- **Superseded decisions, proposals abandoned as a whole, and documents that belonged only to a deleted module.** Record the reason, the scope, and what replaces them, then archive the whole document.

Content that is waiting, blocked, or still constraining current behavior is not archived automatically because it is old or over its size budget. A knowledge page that no current document links to is reported as `orphan-page`: link to it from the navigation, merge it into another page, or, once it is confirmed to have no current responsibility, archive or delete it.

Archiving never moves files by hand. First run `archive <original relative path>` and check the preview: the history root chosen from the project's configuration, the conflicts, and the link rewrites. Then add `--apply --expect <plan_sha256>` to carry it out. A summary is appended to an existing history index only when `--summary` is given; the history root, the choice of index, and the requirements for the table are in the [archiving rules](reference.md#archiving-preview-first-then-apply). Keep the original file name and relative directory; do not reclassify module documents into another mirrored set of directories. When the target already exists, stop and do not overwrite it. Before creating a document, check the matching history with `check-new <path>`.

## Keeping the number of documents down

What can be written as a section of an existing file does not get a new file. Only two situations justify a separate document: the content has its own lifecycle and needs to be scheduled, updated, and archived on its own; or several people need to write it at the same time and would conflict in one file. If every step creates a file, the number of files multiplies with the rounds, the participants, and the models.

Each rule has exactly one authoritative text; other places link to it and do not copy the full explanation. `AGENTS.md` may restate hard rules that directly cause errors when ignored, but each restatement links back to the authoritative text, and following a key rule must not depend on opening a link: key rules have to be directly visible in `AGENTS.md`. Registers that keep growing (deferred gaps, issue lists, history indexes) are searched by ID or keyword, and only the matching lines are read; the entry states which files are of this kind and which keywords to search them with.
