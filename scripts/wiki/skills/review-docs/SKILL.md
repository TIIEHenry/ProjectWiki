# 核对项目文档

以当前业务项目为工作对象。先读该项目的 `AGENTS.md` 和相关入口，确定主题、相关文档和实现范围；不把技能所在的 ProjectWiki 源仓库当作审查对象，也不要求回源读取规范。

文档流程遵循[共享流程与项目适配](../../workflow.md#共享流程与项目适配)；核对项目规则时按该节判断例外与尚未迁移的冲突。

## 确定范围与依据

从用户指定的页面、模块或问题出发，沿相关引用和关键词找到权威正文、需求、设计、决策及对应实现。默认只核对这个范围，不因“文档体检”扫描全仓或新建审计报告。

先辨别每份材料的职责和时态：需求可以描述尚未实现的目标，设计可以记录已接受的约束，代码和配置描述当前实现，测试及运行记录只证明其实际覆盖的条件。归档材料用于解释历史，不能直接当作当前规则。

核对项目已有的授权、需求状态和决定，避免以新旧程度或文件类型机械决定谁对谁错。实现与文档不同时，先判断是实现偏离、目标尚未实现、正文过时，还是证据不足；不能只因代码不同就修改需求或设计。

## 逐项核对

- 对照文档中的行为、接口、配置默认值、限制和示例，定位相关代码、测试及配置；检查调用方与提供方是否采用同一约定。
- 查找互相矛盾的现行描述、缺失的适用条件，以及多处独立维护同一规则的情况。重复引用不等于重复权威；有意保留的目标与现状区别也不算矛盾。
- 对每个发现记录可复查的来源路径与行号、具体差异、读者或行为受到的影响，以及建议修改哪一处、为何修改。来源冲突或缺少决定时说明待确认点，不把推测写成成立的问题。

默认在会话中按影响列出发现，并说明实际阅读范围、证据和未核对项。没有发现时也只说明该范围内未发现问题，不宣称全项目一致。

## 正式审查与修复

用户明确要求正式审查时，按[审查规则](../../workflow.md#审查)组织记录；问题字段按[审查问题](../../formats.md#审查问题)填写。正式核对须由非作者的人或 Agent 完成；作者复读不能算独立核对，不能替他人填写签收。无法安排独立核对时保留待核对状态并报告限制。

用户已授权修复时，按授权范围更新权威正文和受影响引用，不重复索取确认。涉及目标或决定变化时按[同步文档规则](../../workflow.md#决定或设计变化时同步文档)处理；尚无授权改变的产品决定只报告差异和建议。

保留无关未提交改动；默认不改源码、不创建提交、不推送。已有请求授权相关操作时沿用其范围。

## 验证与反馈

结构检查只能核对链接、格式等工具规则，不能代替上述语义核对。只读核对不强行补测试或运行全量验证；确需实测时只运行授权范围内的相关检查，并考虑构建、生成文件等副作用。发生文档修改时，从当前项目验证入口选择相应检查，命令见[工具入口](../../README.md#常用命令)；需要保存验证记录时使用 `verify` 的实际输出。

区分静态阅读、实际执行的测试和人工核对。未运行测试就不称行为已验证，不伪造需求证据或人工签收。反馈发现、修复位置、实际检查输入与范围、结果和剩余限制；无需另建一份报告。
