# 开发流程规则

本篇是接入项目的 Agent 在开发时要遵守的流程规则。工具拦得住的（链接、状态行、需求编号格式）由 `check` 和 `remind` 检查；工具拦不住的（什么时候写决策记录、决定变化时同步哪些文档、审查怎么分工、哪些内容该归档）写在这里。接入项目的 `AGENTS.md` 链接本篇，不要整段抄写。

命令查 [README.md](README.md)，配置字段和规则名查 [reference.md](reference.md)（按名称搜索，不整篇读），状态行、核对行、需求条目、审查问题、待处理项这些工具读取的固定写法查 [formats.md](formats.md)，开发流程规则看本篇。

决策记录（Architecture Decision Record，ADR）解释一项重要选择为什么成立；计划（plan）是一项工作的执行步骤；路线图（roadmap）是项目的方向和先后顺序。

## 共享流程与项目适配

接入后的文档开发流程以本篇为准，项目的 `AGENTS.md` 和开发入口指向这里。接入或升级涉及流程变化时，对照本篇清理原有要求，在原入口删除或替换重复、冲突的条目，并同步依赖这些条目的检查器和其他读取方。旧规则已经存在或要求更严格，都不是保留理由；不能默认把两套要求叠加执行。

确有共享流程未覆盖的项目需要时，才补充项目规则或声明例外。在原有规则入口写明对应的共享规则、具体触发条件和必要理由；已有权威正文的只链接过去，不另建例外清单，不要求每次任务重新说明。条件不再成立时取消例外。没有这些依据的旧要求应在接入时清理，不能因暂未处理就视为有效例外。

业务、接口和安全约束不因文档流程统一而删除。执行套件用于派工、恢复和并发控制的记录，按[任务记录与状态页](#任务记录与状态页)核对实际读取用途；改变协议前迁移读取方并验证。保留必要用途不代表保留重复记录，也不代表所有套件步骤自动成为文档流程的例外。

日常任务发现尚未清理的冲突时，将它作为接入缺口，指出冲突条目及受影响操作。本次授权包含流程调整的，修订原入口和相关读取方后按共享流程执行；不包含的，继续无冲突的工作，说明受阻部分及需要补齐的接入。不能擅自忽略当前明确指令或绕过钩子，也不能为完成任务临时叠加两套流程或宣布旧规则长期优先。

目录、编号和已登记的状态写法属于项目配置适配，不构成流程例外。本篇的目录示例用于没有既有布局的新项目；实际位置以项目入口和 `docs/wiki.json` 的登记为准，字段见[配置与规则](reference.md)。复用已有位置，不因示例路径不同新建第二套目录；配置缺失或冲突时先补齐相关登记。

## 需求到验证的顺序

新功能和行为变化按"需求 → 实现与测试 → 验证"推进，设计和计划按影响范围补充。局部修复不改已有需求的，不新建需求条目，在现有计划或提交里引用相关编号即可；修复中发现需求本身有缺口时，回到第 1 步。

1. 在需求文件里新增或修改条目，写出可检查的验收条件，状态写"提出"。编号按 [formats.md](formats.md) 的编号分配取号，并行分支撞号时由后合并的一方改号。
2. 需求边界和验收条件明确后，状态改"已接受"。需要解释结构、接口、依赖或兼容性变化时，更新相关设计，并用"对应需求：<编号>"引用。
3. 涉及多步骤协作、重要风险、交接或长时间工作时建立计划。计划开头写"覆盖需求：<编号>"，每个步骤写明它满足哪些验收编号。边界明确、没有重要风险或契约变化，也不需要多步骤协作或交接时，可以只用需求条目和测试完成追踪；已有正文失实时仍要更新。
4. 实现时测试在说明文字里写验收编号；完成后把需求状态改"已实现"。
5. 跑完测试或完成人工核对后，在需求条目补"证据："链接。标了"（人工验证）"的验收同时写一行验收核对记录，再把状态改"已验证"。能写测试的验收条目写测试，不用核对记录代替。

已有设计写"对应需求："、计划写"覆盖需求："、测试写验收编号，用编号串起相关记录。`check` 会报出引用了不存在的编号、没有测试引用的验收条件，不因缺少设计或计划要求新建文档。条目写法见 [formats.md](formats.md) 的需求条目。

## 任务记录与状态页

任务的步骤、进度和验证各自只维护一份权威记录，优先复用已有计划或任务记录；普通修复可以只在提交信息中保存依据和验证结果，不要求新建计划。不要因每次提交机械更新状态页，也不要把历史流水留在当前总览中。清理已有总览时，先删除重复记录、缩减内容和更新次数；拆成更多文件不是必要步骤。

先按实际读取方和用途区分协调摘要与执行协议记录。供调度 Agent 或程序用于派工、恢复、并发控制、交接或验收追踪的记录，按执行套件契约保留；手工维护的状态、队列或槽位登记也可能承担这些用途。每项事实仍只在一处维护，其他页面链接原记录或由工具生成视图。不能因文件名含 `status`、看板或目录名为 `loop` 就一概删除或一概豁免。下文的短状态页指协调摘要，不代替执行协议记录。

调整已有记录的路径、字段、更新触发条件或停用方式前，先核对读取方，同步迁移并验证；套件依赖的固定入口和已有映射可以保留。是否拆成模块记录也要考虑实际读取方，不能仅为减少文档就改断套件的读取路径。当前总览与历史流水仍应分开，仍用于恢复或验收的证据不因任务结束就移走。

只有确有全局协调需求，且已有计划、任务记录和模块 README 无法承担时，才建立或保留一份短状态页（如已有的 `status.md`）。它只放当前任务链接、跨模块依赖和待决事项；任务详情留在原记录中，只在这些协调信息变化时更新。协调需求消失后，把仍有用途的链接并回开发入口，停用状态页；已结束的完整过程记录按归档规则处理，其余修订历史由 Git 保留。

多个模块长期独立推进、读者长期只关心局部，或多人编辑总览持续发生冲突时，才评估模块状态页。只有现有计划和模块 README 无法承担的局部协调用途，才值得单独成页；沿用项目已有模块标识和命名规则，不默认给每个模块建一份，不为拆分另增路径或映射配置。模块状态页同样只维护协调信息，不再复制任务进度。

## 与执行套件共用开发入口

ProjectWiki 维护当前知识、需求与记录的追踪、文档检查和归档。执行套件维护派工、任务执行状态、并发冲突与槽位、恢复和收口。本地进程号、锁、缓存和日志由套件的运行目录管理，不抄进知识页。

同时采用两者时，在根 `AGENTS.md` 指向的既有开发入口登记项目绑定；新项目默认用 `dev/INDEX.md`，已有入口不必改名。绑定是供人和 Agent 阅读的角色与实际来源说明，不是 `docs/wiki.json` 的新字段，也不是另一套任务清单。按套件实际读取需要说明：

| 角色 | 入口要说明什么 |
|---|---|
| 任务来源 | 从哪份计划、需求、问题或提交任务取工作；用什么编号或链接识别原任务 |
| 执行与协调记录 | 谁维护派工、执行状态、冲突范围、槽位和恢复依据，实际记录在哪里；套件的规则入口在哪里 |
| 待处理项来源 | 新发现的问题进入哪个已有收件箱或问题系统；已有条目怎样关联原任务 |
| 验证入口 | 从哪里运行项目验证、在哪里保存结果与限制 |
| 归档约定 | 哪些记录结束后归档、归档到哪里；恢复或验收读取方何时不再依赖原位置 |

尚未登记绑定的旧项目按既有套件契约工作；采用绑定后，以声明的实际来源为准。只登记实际采用的来源，未采用的角色明确写“无”或“未采用”；不为填表创建空文件。路径、编号和状态含义沿用项目已有结构与配置；固定格式的读法由对应提供方规定。消费者先读入口绑定，再按声明找到原记录，不能在接受绑定后仍强制读取另一套默认路径。套件无法读取现有来源时，先调整消费者或选择已有可用映射，不能宣称已经适配。

每项事实由一份记录负责。计划可以保存实施步骤，套件任务记录保存派工与执行状态，槽位登记保存当前占用范围，三者用途不同可以共存；用原任务编号或链接关联，摘要只链接或生成。计划的生命周期状态和套件任务的调度状态分别解释，不互相覆盖；任务执行完成也不自动表示需求已验证、计划可以归档或槽位已经释放。各项结束条件按各自职责核对，需要的步骤可由同一次操作完成，不要求重复写两份完成记录。

接入时选一项真实任务，沿绑定依次核对取任务、派工或接续、验证、结束与归档：原任务能找到，执行状态和占用范围有唯一更新位置，未完成事项有去向，归档后仍可查到证据。未实际运行套件时，只能报告已核对绑定或文档检查，不能报告派工、恢复或并发执行已经通过。套件特有的阶段、命令和恢复规则在套件自己的接入说明维护，本篇不复述。

## 决定或设计变化时同步文档

读者和 Agent 按当前的需求、原则和设计工作，ADR 只解释原因。所以决定或设计发生变化时，在同一次改动里更新所有仍然描述旧结论的现行文档，不能只改 ADR、只改代码，或把同步留到以后。

| 发生了什么 | 同一次改动中要做的事 |
|---|---|
| 采用一份新 ADR | 按新结论修改受影响的需求、原则、设计和模块入口；`AGENTS.md` 里复述该规则的条目一起改；需要解释原因的设计页链接到这份 ADR |
| 一份 ADR 被替代 | 新 ADR 写明替代了哪一份和原因；旧 ADR 只把状态改"被替代"并链接新 ADR，不改写当时的理由；现行文档里指向旧 ADR 的链接改指新 ADR |
| 一份 ADR 被废止、没有替代 | 旧 ADR 状态改"废止"并写明原因；现行文档删除依赖这项决定的内容，或改写成现在的做法 |
| 设计改变推翻了某份已采用 ADR 的结论 | 先补一份新 ADR 替代它，再按"被替代"那一行处理。不能让设计页和 ADR 都标为当前、内容却互相矛盾 |
| 设计改变但不涉及任何已采用的决定 | 原位修改设计页即可，不新建 ADR |
| 代码行为改变了文档描述的接口或规则 | 和代码一起提交对应的需求、设计或模块 README 修改 |

已经结束的计划和归档文件记录的是当时情况，不随新决定改写。

**找出受影响的文档要走两路，只查链接会漏掉直接复述结论的地方。**

1. 查链接：找到现行文档里链接这份 ADR 的地方。先核对 `.ignore` 是否排除了项目已登记的历史根，再用 `rg '<ADR 文件名>'` 搜索现行文档；也可以用 `archive <ADR 路径>` 的只读预览查看工具能够识别的入链，不需要真的归档。
2. 查关键词：按这项决定的关键词搜索现行文档，找出没有链接、但直接写了旧结论的地方，尤其是 `AGENTS.md`、需求页和模块 README。

工具只能确认链接存在、路径有效，判断不了内容和新结论是否一致，所以提交者要通读改动范围，评审时也要核对。

**什么时候写 ADR。** 选择会持续影响结构、接口、依赖或兼容性，并且存在需要解释的替代方案时，写 ADR，用背景、替代方案、决定、后果四部分。还没定的取舍先记在已有任务或计划里。沿用项目已有的决策入口；没有既有布局时，只影响单个模块的放模块 `docs/decisions/`，跨模块的放根 `docs/decisions/`。新项目用描述主题的文件名，不依赖全局顺序号；已有编号保留。ADR 不是所有工作开工前的固定手续；已采用的决定可能长期有效，不因对应计划完成而归档。

## 审查

针对指定页面或主题的文档核对，默认在会话中反馈依据、问题和未检查范围，不新建审查目录。用户要求正式审查，或明确需要持续跟踪问题、独立核对和签收时，采用下面的记录流程；一次阅读核对不能直接算作独立核对或签收。

审查用来系统地找问题，可以由人发起，也可以由多个 Agent 并行做。目录结构和问题写法见 [formats.md](formats.md) 的审查问题。

1. **准备。** 在项目已有审查入口下选择与 `reviews` 配置匹配的具体目录，新项目默认用 `dev/reviews/<开始日期>-<主题>/README.md`，目录说明见[审查问题](formats.md#审查问题)。在 README 写要回答的问题、范围、基准提交和分路方式。负责汇总的人在分路表里给每一路分配路号；中途追加的路也先登记路号，执行者再开始写。路号由汇总人统一分配，并行的执行者才不会取到同一个号。
2. **发现。** 每一路只写自己的分路文件，每条问题一个小节，状态"待核对"。不同路发现同一个问题时，后发现的那条在核对时判"重复"。
3. **核对。** 由不是作者的人或 Agent 打开对应代码和文档，逐条判定，在问题小节的核对表里追加一行，再改状态行。判定为已知时链接到已有的方案、缺口或决策，不重新处理。核对分组写在 README 里，各组负责的路不重叠。
4. **方案与签收。** 为成立和收窄的问题写方案，写在问题小节里；跨多条问题的修复建同目录下的 `plan-<主题>.md`。签收写进问题小节和 README 的汇总表，汇总表只由汇总人更新。
5. **实施与结束。** 签收后方案就是执行计划，不另建重复记录进度的看板；执行套件所需的冲突范围和槽位登记按[执行协议用途](#任务记录与状态页)保留。仍然有效的结论写回设计、需求或决策，README 状态改"已完成"，再用 `archive` 把整个目录归档。

**核对人不能是作者。** 复查、换人、换模型都在核对表里追加一行，不新建文件。一次审查的文件数大约等于路数加一：轮次、模型、日期写进表格，不写进文件名。能写进已有分路文件的一节，就不新建文件。后续针对同一主题的审查新建一个日期目录，并在 README 里链接上一次，不追加到旧目录。

## 生命周期与归档

现行知识原位维护：需求、原则、模块结构和当前接口契约持续在原处更新，普通修订由 Git 保留历史，不因一次修改或一次任务完成就整页归档。

项目登记的历史根（新项目默认 `archive/`）主要保存已结束的开发过程材料。按下面的时机结束并归档：

- **计划。** 状态变为已完成或已取消后归档。归档前先让状态行和步骤清单一致：状态已是完成却仍有未勾选步骤的，给每个剩余步骤一个去向（另开计划、写回当前知识、或明确取消）；步骤已全部完成却仍标执行中的，改为完成。工具只认状态行，发现不了这种不一致。
- **待处理项。** 分诊后要有结束方式：转成了哪份计划、写回了哪篇知识、和哪条重复，或为什么不处理，把去向写进条目，状态改"已完成"后归档。归档而不是删除，因为"不处理"的理由以后还会被问到。
- **审查目录。** README 状态改"已完成"、所有方案都已实施或转出之后，把整个目录一次归档；只要还有一条方案没结束，就整个留在原地，不拆开归档。
- **实验报告和验证原始记录。** 工作结束后可归档，可复用的结论整理进当前知识。
- **被替代的决定、整篇废弃的方案、已删除模块的专属文档。** 记录原因、适用范围和替代目标后整篇归档。

正在等待、阻塞或仍约束当前行为的内容，不因时间久或超出篇幅预算而自动归档。没有任何现行文档链接的知识页会被报 `orphan-page`：从导航链接它、并进另一页、或确认没有当前职责后归档或删除。

归档不手工移动文件。先运行 `archive <原相对路径>`，核对预览按项目配置选定的历史根、冲突和链接改写，再加 `--apply --expect <plan_sha256>` 执行。只有附带 `--summary` 才向已存在的历史索引追加摘要；历史根、索引选择和表格要求见[归档规则](reference.md#归档先预览再执行)。保持原文件名和相对目录，不把模块文档重新归类到另一套镜像目录；目标已存在时停止，不覆盖。新建文档前用 `check-new <路径>` 检查对应历史。

## 控制文档数量

能写成已有文件里的一节，就不新建文件。只有两种情况单独成文：这部分内容有自己的生命周期，需要单独排期、更新和归档；或者需要多人同时写，放在一起会冲突。每做一步就新建一个文件，文件数会随轮次、参与者和模型成倍增长。

同一条规则只指定一份权威正文，其他地方链接过去，不复制完整解释。`AGENTS.md` 可以复述忽略后会直接导致错误的硬规则，但每条复述都链接回权威正文，而且遵守关键规则不能依赖继续打开链接——关键规则要在 `AGENTS.md` 里直接可见。会持续变长的登记表（延期缺口、问题清单、历史目录）按编号或关键词搜索，只读命中的行，入口里写明哪些文件属于这一类、该用什么关键词查。
