# 中文技术文档规范

## 适用范围

本规范适用于需求、原则、设计、指南，以及需要长期阅读的决策说明。执行记录可以简短，但仍需区分事实、推测和待处理事项。

## 写之前

先明确读者要解决的问题、文档适用范围和已有权威正文。检索当前知识及对应历史，确认需要新建文件，还是应该修订现有页面。

为正文选择能描述内容的标题。摘要用一两句话说明内容，不记录开发流水。阅读时机写在索引或导航链接旁。

## 正文写法

- 用具体对象作主语，直接描述动作、条件与结果。
- 解释设计理由时给出问题、约束与取舍。保留必要细节，删去重复结论。
- 使用完整段落。并列项目适合列表，比较关系适合表格；不要把每个句子都拆成独立段落。
- 同一概念使用同一名称。首次出现的必要缩写应解释，项目内部称呼应换成外部读者能理解的表达。
- 区分规范与现状。目标能力尚未实现时明确说明，不能把计划写成已经存在的行为。
- 区分观察与推测。给出能够复查的来源，未验证的判断注明依据和限制。
- 操作指南写清前提、步骤、预期结果和验证方法。示例代码应与当前实现一致。
- 排查类指南按读者看到的症状组织，每节标题就是一个症状，正文先写优先检查什么、再写证据在哪里，不先写系统概述。例子见 NoteBox 的[故障维护指南](../../demo/docs/guides/maintenance.md)。条目多时可以用"症状 / 优先检查 / 证据"三列的表格。
- 跨模块契约写明提供方和消费方：哪个模块定义它，哪些模块依赖它，改动时要通知谁。
- 项目里反复出现的内部名称收进术语表（例如 `docs/glossary.md`），每条写定义、适用范围和权威正文的链接。正文第一次用到时链接术语表，不在每篇文章里重新解释。

## 截图、原型和线框

正文可以引用任何格式的资产：截图、HTML 原型、`.canvas.tsx` 线框、导出的 JSON。资产放在引用它的文档旁边，同一功能的资产多了再建子目录，不预设固定的 `assets/` 结构。

- 引用时写明用途，例如"线框：底栏分隔线的布局"或"竞品截图，仅作对照"。
- 用文字写出从资产里得到的结论：尺寸、顺序、状态、交互规则。读者和 Agent 不一定能打开或看懂图片和原型，资产只作佐证，规则以正文为准。
- 资产还描述当前界面时，它和正文一样原位维护；整套设计被替代后，连同正文一起归档。不要每改一版就归档一份旧图，旧版本由 Git 保存。
- 检查工具会核对资产链接是否存在，但不读资产内容。

## 常见改写

| 问题 | 不合适的表达 | 建议表达 |
|---|---|---|
| 空泛铺垫 | “值得注意的是，本方案能够有效赋能开发流程。” | “索引提供源码和测试入口，开发者可以从模块说明定位修改位置。” |
| 翻译腔 | “对配置的加载进行执行。” | “加载配置。” |
| 内部行话 | “这刀补齐闭环，下轮再收口。” | “本次修改补充超时处理；下一项任务验证重试失败后的行为。” |
| 夸大效果 | “全面解决所有文档一致性问题。” | “检查本地链接和已登记的配置字段；设计语义仍需审查。” |
| 无依据的进度摘要 | “阶段 12 全绿，阶段 13 已完成。” | 在知识页说明当前行为，将执行结果写入对应任务记录。 |
| 主观形容 | “这是一个优雅而强大的设计。” | 说明它减少了哪些重复内容，以及采用它的条件。 |

句首连接词只在确实表达逻辑关系时使用。删除没有新增信息的总结、预设反驳和口号式句子。避免逐词照搬外语句式，必要时拆开长定语并调整语序。

## 写之后

1. 从标题到结尾阅读全文，确认一个不参与当前会话的开发者也能理解。
2. 核对术语、链接、代码示例和适用范围。
3. 检查是否夹带任务流水、过时示例或未解释的内部缩写。
4. 检查每个判断是否有明确对象、条件和依据。
5. 运行文档检查，处理结构问题，再复核改写是否改变原意。

关键词搜索可以辅助发现可疑表达，但不能据此断言文本由 AI 编写，也不能把所有连接词机械列为错误。文风审查以逐句阅读为准。
