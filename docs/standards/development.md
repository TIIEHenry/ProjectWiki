# ProjectWiki 开发规范

## 修改前

阅读受影响的需求与设计，确认修改属于规则调整、工具行为变化、模板变更还是示例变更。接续已有工作时，核对 [待办](../../TODO.md) 和工作区里的未提交差异。

本仓库是文档系统本身，不按接入项目运转：不建计划、路线图、待处理项和归档。没做完的事写进 `TODO.md`，对接入项目有影响的变化写进 `CHANGELOG.md`，其余过程留在提交信息里。

改动要让两个使用场景保持一致：复制模板接入一个新项目，以及参考项目 `demo/` 的运行。新增强制字段或门禁时，先在 demo 或一个临时小项目上验证它确实必要。

## 实现要求

- 本地工具以 Python 3.10 及更新版本运行，第一版仅使用标准库。
- 检查保持只读。预览、生成和写入接口清楚区分，不自动暂存或提交。
- 配置完整解析，字段错误明确报告。不能在解析失败时静默采用另一套默认值。
- 路径按目标仓库与引用所在文件解析，检查大小写，不使用仓库根回退来掩盖错误相对链接。
- 暂存检查的配置、正文和链接目标来自同一 Git 索引快照；缺失时不能读取工作区内容补齐。
- 归档保留原路径和文件名。预览展示冲突与引用影响；执行时用计划哈希核对预览后没有变化，目的地已存在时不写。
- 不清理其他协作者的文件。共享工作区按文件范围分工。
- 合并或变基时，两边都改过的文件要做真正的三方合并。不能默认整份采用一边（`checkout --ours/--theirs`、`-X ours/theirs`），否则另一个人或 Agent 的改动会无声丢失。
- 留下占位实现、空分支或 `TODO` 时，在代码旁写明为什么这样做、影响哪些行为、什么时候清理，并在 `TODO.md` 里登记。没有这些说明的占位不能进入主分支。

## 验证与文档更新

```bash
python3 scripts/wiki/wiki.py verify --root .
```

验证命令只登记在 [`docs/wiki.json`](../wiki.json) 的 `verify` 里：工具测试、demo 测试、本仓库规范文档、demo 和项目模板的 `check`，以及 demo 生成目录的 `index --check`。只需要其中几项时写名称，例如 `verify tests check`。

工具行为变更需要运行相关反例测试；配置或目录变更需要检查实际接入范围；模板变化需要在临时目录复制验证。仅修改文字时，检查引用与表达即可，不重复运行无关代码测试。

行为、接口或目录职责变化时，原位更新对应规范，同一次改动里同步模板和 demo。规范没有变化时，不为形式完整而新增文档。

## 验证记录

需要记录验证结果时（例如写进提交信息），用 `verify` 的输出，不手写：它写明 Git HEAD、未提交文件数和被测文件的哈希，命令结果来自实际运行。人工核对的内容和已知限制写在这段输出后面。

检查通过只能说明实际覆盖的规则成立。未运行的检查、无法访问的范围和不支持的语法应明确列出。

已知失败要写明失败的测试或命令、复现方式和退出条件，也就是满足什么条件后这条失败应当消失。"改动前就是红的"只能说明失败不是本次引入，不能作为一直不处理的理由。暂不处理的失败登记到 `TODO.md`。

## 文档表达

新建与修改稳定知识时遵守[中文技术文档规范](writing.md)。模板中的提示语也需要明确、简短，避免诱导 Agent 生成空泛的背景、重复总结或无实际内容的章节。
