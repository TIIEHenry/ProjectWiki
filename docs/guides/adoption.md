# 接入 ProjectWiki

对应需求：PW-10、PW-27。

本指南供接入项目的开发者与 Agent 使用。目标是建立能支持真实开发任务的最小文档体系。

用户要求给指定项目接入 ProjectWiki 或补齐未完成的接入时，Agent 可使用[接入技能](../../scripts/wiki/skills/adopt-projectwiki/SKILL.md)。首次接入从 ProjectWiki 源仓库打开，已复制工具的项目从本地 `scripts/wiki/skills/adopt-projectwiki/SKILL.md` 打开；这不代表宿主已原生安装技能。技能写入的对象是用户指定的目标项目；源仓库只提供模板、工具和本指南。源仓库位置来自用户给定路径或工作区中已定位的来源，缺少时只暂停依赖模板或完整指南的步骤，不自行构造路径。接入不包含自动升级或未经授权的提交、推送、全局配置与执行套件操作。

## 1. 阅读 ProjectWiki 并调查目标项目

先读[设计原则](../principles/document-system.md)、[接入项目的目录](../design/document-model.md#接入项目的目录)、[开发流程](workflow.md)和[参考项目](../../demo/README.md)。

进入目标仓库后，检查现有 `AGENTS.md`、README、模块、文档、开发记录和历史目录。找出当前权威页面、重复说明与仍有用途的旧材料，并分别处理已有内容和已有流程。接入后的文档开发流程以 ProjectWiki 共享流程为基线，按[共享流程与项目适配](../../scripts/wiki/workflow.md#共享流程与项目适配)完成规则迁移。

已有的有效正文、需求编号和历史记录优先登记，不为通过检查批量改写。保留内容和路径不表示保留旧流程。对每条默认每次任务或每次提交都要执行的要求，检查它解决什么问题、何时触发，以及是否和共享流程重复或冲突；按共享流程修改原有规则入口及其读取方，不默认把两套要求叠加。确有必要的项目例外按共享流程的适配规则写在原入口。不要同时要求计划、状态页和看板重复记录同一项进度。

已有检查器也按实际覆盖范围、读取的输入快照和失败条件核对。确认两项检查等效时只保留一项；工作区检查与暂存检查读取的内容不同，不能仅因规则名称相近就当作重复。将清理后的规则直接写回目标项目原有入口，不另建一份长期维护的流程清单。

项目已接入执行套件时，先核对哪些 Agent 或程序读取状态、队列、看板和证据，按[任务记录与状态页](../../scripts/wiki/workflow.md#任务记录与状态页)区分协调摘要与执行协议记录，再决定是否合并、拆分或停用；已有固定入口和映射不能因名称相似就删除。

不要把 ProjectWiki 自己的产品需求复制成目标项目需求。文档结构可以复用，业务内容必须依据目标项目实际情况编写。

执行套件与 ProjectWiki 同时使用时，按[共用开发入口](../../scripts/wiki/workflow.md#与执行套件共用开发入口)登记实际来源和职责，再按套件自己的接入说明迁移读取方。先保留能工作的映射，例如 `dev/roadmap/active/` 的计划、`dev/progress/` 的待处理队列和 `dev/parallel/active/` 的占用记录；这些路径是已有项目的例子，不是所有项目必须建立的目录。轻量项目也可以直接复用需求、现有计划或提交任务，不为接入建立阶段、状态页或决策记录。用第 2 步选出的任务实际核对两套流程是否能接续。

## 2. 先建立两个真实阅读路径

选一项功能修改和一项维护问题，明确需要的需求、原则、设计、代码与测试。先用这两个任务检验目录与模板，避免一次建立大量空页。

每条路径应让读者明确目标、约束、实现入口和验证方式。增加一个反例：局部配置修改会影响另一个模块时，相关契约能否被找到。

## 3. 建立最小结构

参考 [`templates/project/`](../../templates/project/README.md)，按目标项目需要创建根 `docs/`、`dev/`、`archive/`。原有模块布局保持不变，单模块知识继续靠近源码。

一个新的、小型项目可以采用模板中的合并页面。内容增多后，再按需求、原则、设计和规范拆分。已有有效文档可以直接登记，不要求先改名或搬家。

**旧目录去向。** 旧仓库常有一批模型里没有直接对应位置的目录。判断依据只有三条：仍描述当前行为的放 `docs/`；记录过程、会过期的放 `dev/`；整篇已经失效的放 `archive/`。放在 `docs/` 下的目录会被当成现行知识解析，所以模板和过程材料不要留在 `docs/`。常见旧目录按下表处理，一次整理不完的登记为过渡（见下一段的过渡表），分批做。

| 旧目录 | 建议去向 |
|---|---|
| `docs/systems`、`docs/architecture`、`docs/reference` | 都是当前知识，归 `docs/`。保留即可，按模块登记或留在根 `docs/`，不必搬动 |
| `docs/modules` | 这是模块镜像目录。全局模块表直接链接各模块入口，把镜像里的内容并进对应模块的 `docs/` 后删掉镜像；一次并不完的，先把镜像登记为过渡，逐个模块迁 |
| `docs/templates` | 模板不是现行知识。放 `templates/` 或对应模块内，不要留在会被当成现行知识解析的 `docs/` 下 |
| `dev/progress`、`dev/roadmap`、`dev/reports`、`dev/iterations` | 都是过程材料，归 `dev/`。会持续变长的登记表按编号或关键词检索、只读命中的行，整页失效后归档 |
| Agent 操作手册、playbook、skill、runtime（例如 `dev/loop/` 下成批的篇目） | 放 `dev/` 下它们自己的目录，不要放 `docs/`。工具或技能按默认路径生成到 `docs/` 时，改配置改掉默认路径，不能改的在 `AGENTS.md` 写明生成后搬进 `dev/` |

使用模板前阅读[模板说明](../../templates/README.md)。复制单个文件时检查目标是否已存在，合并有效内容，并按第 1 步核对和清理流程规则，不用模板整份覆盖原文件。

**旧仓库的过渡表。** 已有大量文档、同一主题有好几篇，而这些文档又不能一次整理完时，先建一张"现行权威表"，例如 `docs/current-sources.md`。每个主题一行，写三列：主题、现行权威文档、不要再参考的旧文档。Agent 和新成员遇到同主题的多篇文档时，只读权威列。之后每归档一篇旧文档就删掉表里对应的一格，所有主题都只剩一份正文时，整张表也一起删除。这张表只用于过渡，不能变成长期维护的第二份导航。

过渡表只回答"同一主题该读哪一份"，只有这三列，不承担别的内容。读旧文档时发现里面的行为更正——"其实现在的做法是 X"——要把这条更正写回现行权威正文，不要把更正堆进过渡表的格子，否则表会膨胀成一份勘误表（已出现过一张 15KB、三十多行、格子里全是行为更正的 `current-sources.md`），而真正的正文反而没更新。表只管导航，所有主题收敛到一份正文后整表删除。

**停用说明。** 一篇旧规范被新规则取代，但仍有外部链接或书签指向它时，不要留一个空文件，也不要把它删掉让链接失效，改写成一段停用说明：一句话说清本文不再规定什么、改读哪里，再列出不要再执行的旧规则。例如：

```markdown
# 标题校验规范（已停用）

本文不再规定标题长度和字符校验，改读 docs/design/title.md。

下列旧规则不要再执行：
- 不要再按旧文的"标题最多 20 个字符"校验，长度上限见新文。
- 不要再引用本文里的正则，它和现在的实现不一致。
```

停用说明不复制新结论，只做指路；等到确认没有外部引用后，可以按生命周期规则整篇归档。

**检查 AI 工具的输出位置。** 一些 Agent 技能会按自己的默认路径写计划或报告，例如写到 `docs/<工具名>/plans/`。接入时搜索 `docs/` 下由工具生成的目录，把内容移到 `dev/`；能改配置的工具改掉默认路径，不能改的在 `AGENTS.md` 里写明生成后移走。

**变更日志。** 项目已经有 `CHANGELOG.md` 时保留它，并在 `docs/INDEX.md` 里登记为用户可见变化的记录。有发布流程的项目，建议在发布脚本里检查当前版本是否已经写进变更日志，没写就停止发布。

**登记接入起点。** 旧仓库有上百份没有状态行的计划、没人链接的旧页面，或者目录里的文件数早已超过预算时，不要把新规则限在 `dev/plans/wiki/` 这类专门的子目录里，也不要给已完成的计划换一个不触发提醒的状态。接入提交完成后，在 `docs/wiki.json` 里写 `"adopted_at": "<接入提交>"`：那时已有的文件不报缺少状态行和孤儿页，也不计入目录预算；新文件照常检查；旧计划的归档提醒合并成一条，写出数量。之后按 `remind --all` 列出的清单，每次处理几份。范围见[接入起点](../../scripts/wiki/reference.md#接入起点)。

**已有 frontmatter 的状态字段。** 计划和决策记录已经在 frontmatter 里写状态时，不要在每篇里再补一行状态行，那样一份工作就有两处状态，没人对照时会分开。在 `docs/wiki.json` 里登记字段名（`status_frontmatter`），把项目用过的取值在 `status_values` 里映射到状态类别；新写的页面用状态行。两处都写的旧页面，工具会在类别不一致时警告。字段见[配置与规则](../../scripts/wiki/reference.md#配置)。

**仍约束行为的决定。** 现有决策如果放在 `dev/decisions/`，把仍然约束当前行为的决定移到所属知识范围的 `docs/decisions/`。其中若有一份规定以后的决定也写在 `dev/`，用新的决策替代这条约定；知识和行动分开的结论可以保留。文件名写主题，不沿用全局顺序号。

**模块清单。** 用构建入口核对 `AGENTS.md` 和文档里的模块表。手写表会漏掉已经参与构建的模块。这项对账还要人工做，工具目前不读构建文件。

**包含路径的大小写。** `CLAUDE.md` 等文件里的包含路径必须与真实文件名大小写一致。区分大小写的系统不会把 `AGENTS.MD` 解析成 `AGENTS.md`。

## 4. 编写关键入口

`AGENTS.md` 直接写明项目目的、适用的硬规则、默认搜索范围与验证命令，并按项目模板声明共享流程基线。保留项目业务约束；流程重复或冲突按第 1 步完成迁移，不能因为旧入口仍在就默认优先执行旧流程。详细理由可以链接出去，遵守关键规则不能依赖继续打开链接。

在 `AGENTS.md` 中按项目模板保留技能任务表：文档审查、文档整理、知识沉淀、补齐接入与同步文档提交各有一个按需入口，路径均在 `scripts/wiki/skills/`。这些技能操作当前接入项目，不要求每次任务或提交都运行，也不代表宿主已经原生发现技能。完整任务导航见[工具入口](../../scripts/wiki/README.md)。需要宿主技能列表或原生调用时，按宿主支持的方式单独登记入口，仍指向各技能的唯一正文。

根 README 面向人介绍项目和入口。`docs/INDEX.md` 根据任务说明何时读哪篇文档。模块 README 说明职责、相关契约、源码和测试位置。

创建稳定知识时使用[写作规范](../standards/writing.md)：写清对象与条件，解释术语，删除 AI 套话、翻译腔和开发流水。全文读一遍，再运行结构检查。

## 5. 接入本地检查

将整个 `scripts/wiki/` 复制到目标仓库的合适位置，并登记自己的 `docs/wiki.json`。目录里的 `README.md`、`reference.md`、`formats.md`、`workflow.md` 和 `skills/` 要一起复制：目标项目的 Agent 按它们查命令、规则、固定写法与收尾步骤，不需要再打开 ProjectWiki 源仓库。`skills/` 中每个技能目录的 `SKILL.md` 是其唯一正文，由 ProjectWiki 提供，供接入项目使用自己的入口、配置和工作区处理相应任务；模板和项目入口只指路，不另存一份。配置路径相对 `--root` 指定的项目根目录。

配置至少列出知识根、过程根、归档根和入口，并按实际结构登记模块。复制来的 `scripts/wiki/` 是工具的说明，在 `exclude` 里写 `scripts/wiki/**`，否则 `check` 会提示这些 Markdown 没被登记。小模块可以只登记 README；有独立文档目录时再填写模块 `docs`。根项目的检查应排除独立示例或子项目，再单独检查它们。检查工具不应依赖搜索时的忽略范围。

```bash
python3 scripts/wiki/wiki.py check --root .
python3 scripts/wiki/wiki.py doctor --root .
```

也可以先从 ProjectWiki 工具目录检查目标项目，无需立即复制脚本：

```bash
python3 /path/to/ProjectWiki/scripts/wiki/wiki.py check --root /path/to/target-project
```

这里的 `/path/to/` 是命令示例占位符，执行时替换成实际路径，不要把本机绝对路径写进目标项目的正文链接。

## 6. 设置默认搜索与文档创建检查

在目标仓库已有的 `.ignore` 中合并 `/archive/`。归档继续纳入 Git。接入旧布局时，将实际的嵌套历史目录登记为 `archive` 角色，并为这些目录补充精确的搜索忽略规则。

新归档默认使用已登记的根 `archive/`；采用其他名称时，在配置中用 `archive_root` 指定主目标。旧历史根仍参与分类和检查，但工具不推断旧布局与原路径的对应关系，需要按主题另行检索。

新建文档前执行以下命令，将路径替换为待建文件：

```bash
python3 scripts/wiki/wiki.py check-new docs/design/new-topic.md --root .
```

检查匹配主目标下的完整原相对路径。命中历史时返回警告，退出码仍为 `0`；阅读历史内容后判断是恢复、延续还是新主题。当前目标已存在则失败。检查不会把必要标准文件名永久禁用。暂存检查也会检查相对捕获 HEAD 新增的文档，提示同一索引快照中的对应历史。

## 7. 接入提交检查

首先让工作区检查通过。在 Git 仓库中暂存配置、正文和相关文件后，再检查实际暂存快照：

```bash
python3 scripts/wiki/wiki.py check --root . --staged
```

项目没有其他钩子时，复制 `scripts/wiki/hooks/` 并在每个 clone 执行一次 `git config core.hooksPath scripts/wiki/hooks`。已有钩子工具时，把 `check --staged` 加进现有 pre-commit、`remind --staged --message-file "$1"` 加进现有 commit-msg，不要覆盖原有配置。仓库里存在脚本不代表当前工作副本已经启用，运行 `doctor` 查看 `git_hooks` 的结果。配置里还没有 `remind` 时，commit-msg 输出警告 `remind-not-configured`，这次提交成功；阈值和拦截要等第 8 步写好 `remind` 才生效，见[提交时的文档提醒](../../scripts/wiki/reference.md#提交时的文档提醒)。

退出码 `0` 表示本次检查没有错误，可能仍有警告；`1` 表示发现错误；`2` 表示输入或执行条件不完整。钩子须将 `1` 和 `2` 都视为失败。没有 Git 仓库时只能运行工作区检查，不能据此报告提交门禁已通过。

用临时 Git 仓库验证一个反例：暂存区链接仍错误，工作区已修好，提交检查仍应失败。不要用未暂存的修复掩盖实际提交内容。

后续归档时先按[生命周期规则](../design/lifecycle.md)判断资格，工具不检查计划是否完成、决定是否失效。然后运行 `python3 scripts/wiki/wiki.py archive <原相对路径> --root .` 预览冲突和要改写的链接，确认后加 `--apply --expect <plan_sha256>` 执行。配置选定的历史索引已存在且含表格时，可以加 `--summary "<一行说明>"` 同时登记，选择规则见[归档命令](../../scripts/wiki/reference.md#归档先预览再执行)。

## 8. 设置文档同步提醒

在 `docs/wiki.json` 中加入 `remind`，把每组代码路径和描述它的文档登记为一个 `watch`，再设置提醒阈值；需要用户确认的需求、原则和决策文件写进 `ask_user`。字段说明见[配置与规则](../../scripts/wiki/reference.md#提交时的文档提醒)。默认可从 10 次提交或 300 行提醒、30 次提交拦截开始，按实际提醒频率调整。

接入时 `remind` 会把接入之前的代码提交也算进去，一些组可能已经超过拦截线。不要为这笔一次性的历史欠账永久调高 `block_at`。逐组核对文档与代码：需要改的文档在接入提交里一起改，这一组的计数就清零；核对后确实不用改的，在接入提交信息最后一段写 `Docs-Reviewed: <组名>,<组名> 接入时逐组核对，文档与代码一致`，计数同样清零。核对不完的组暂时不写进 `watch`，核对后再加，不要为了清零写一句没有核对过的理由。

提醒对所有 Agent 宿主通用，依靠三处：

1. Git `commit-msg` 钩子在每次提交时运行 `remind --staged`，提醒会出现在提交命令的输出里。
2. 目标项目的 `AGENTS.md` 写明：开始任务时运行 `python3 scripts/wiki/wiki.py remind --root .`；单次代码改动的 `[info]` 提示不要求补复核记录，累计达到提醒阈值时才要求复核，达到拦截阈值时才阻止继续累积；已知文档描述失实时仍在本次修改中更新。处理方式和阈值见[提交时的文档提醒](../../scripts/wiki/reference.md#提交时的文档提醒)。`[user]` 类提醒报告给用户；不得用 `--no-verify` 跳过钩子。
3. 可选：宿主支持会话开始钩子时，让它运行同一条 `remind` 命令，把汇总注入上下文。例如 Kiro 可以创建 `SessionStart` 触发、命令为该命令的 hook；Claude Code 等宿主按各自文档配置。这一步只是让提醒更早出现，没有它前两条仍然生效。

用临时仓库验证：未达累计阈值时，只改代码和测试的普通修复会出现 `docs-not-updated`，不写复核 trailer 也能提交；达到提醒阈值后要求复核；累计量达到拦截阈值后继续改代码的提交失败，更新对应文档或真实复核后通过。阈值与复核记录写法见[提交时的文档提醒](../../scripts/wiki/reference.md#提交时的文档提醒)。

## 9. 给需求编号并接入追踪检查

把目标项目已确认的需求按[需求模板](../../templates/requirements.md)整理：每条一个带编号的标题、一行状态、带子编号的验收条件。已有 PRD 或需求清单时保留原编号，只补状态和验收子编号；编号不是 `APP-01` 这种格式时，在 `requirements.id_pattern` 里登记自己的格式，不要为了通过检查改编号。然后在 `docs/wiki.json` 加入 `requirements`，登记需求文件和测试文件的位置。仓库里有几个产品各自编号，例如引擎和客户端都从 `PRD-001` 编起时，不要关闭追踪，也不要改号：把 `requirements` 写成分组数组，每组登记自己的需求文件、引用它的文档和测试，写法见[需求追踪](../../scripts/wiki/reference.md#需求追踪)。

旧项目第一次运行可能报出大量 `trace-no-test`。先处理 `trace-unknown-ref` 这类错误，处理不完的错误可以记入存量基线；警告不会让检查失败，也不进基线，可以接入后逐条核对测试覆盖并补真实的验收编号。按[开发流程](workflow.md#开始工作)判断是否需要设计或计划；轻量变化可以只用需求条目和测试追踪，工具不因缺少设计引用而要求新建页面。已有设计仍描述相关行为时保持准确，不为了凑齐引用批量写入编号。

## 10. 可选：核对记录与 OKF 导出

运维手册、外部事实、调查结论这类会过期的页面，在标题下写 `核对：agent:<名字>，YYYY-MM-DD。复核期限：YYYY-MM-DD。`，再在 `docs/wiki.json` 的 `verification.review_by_required` 里登记这些路径。需要人工把关的路径登记在 `verification.human_required`。格式见[文档模型](../design/document-model.md#核对记录与复核期限)。

需要把项目知识提供给支持 Open Knowledge Format 的工具时，运行 `python3 scripts/wiki/wiki.py export-okf --root . --out <项目外的空目录>`。导出不改变仓库里的写法，目录和规则见[配置与规则](../../scripts/wiki/reference.md#导出-okf)。

## 11. 登记验证命令与对账

把目标项目必须执行的测试和检查登记在 `docs/wiki.json` 的 `verify` 里，每条命令写成参数数组，必要时写运行目录和环境变量。之后计划的验证记录用 `python3 scripts/wiki/wiki.py verify --root .` 生成，Agent 不再手写命令结果和哈希。`AGENTS.md` 和开发规范里只写这一条命令，命令清单只在配置里维护一处。字段见[配置与规则](../../scripts/wiki/reference.md#验证记录)。

文档里有规则名、配置项、环境变量这类与代码一一对应的名单时，可以登记 `reconcile`，让 `check` 比较两边的名单。先在一处名单上试用，看误报能否用少量 `ignore` 排除；排除项比名单本身还多时，这份名单不适合用正则对账。字段见[配置与规则](../../scripts/wiki/reference.md#文档与代码对账)。

## 12. 链接到其他仓库

系统由几个并列检出的仓库组成时（例如构建用 `includeBuild('../OtherRepo')` 引入相邻仓库），在每个仓库的快速开始里写明约定的检出布局，再按下面做：

1. 跨仓库链接写相对路径，不写本机绝对路径，也不写成行内代码。在 `docs/wiki.json` 的 `repos` 里登记目标仓库，写法见[相邻仓库和子模块](../../scripts/wiki/reference.md#相邻仓库和子模块)。目标仓库已检出时，`check` 会核对目标文件和锚点；没检出时只警告，持续集成只检出一个仓库时也能通过。
2. 子模块不用登记。没初始化时，指向它的链接同样只警告。
3. 跨仓库的契约只在提供方仓库写正文，使用方链接过去，规则见[跨仓库的契约](../design/document-model.md#跨仓库的契约)。复制到别的仓库的 README，改成指向规范源的短说明。
4. 链接写好后，先用 `check --require-repos` 在检出全部仓库的机器上跑一遍；`check` 提示"Written as"的断链，是少写或多写了 `../`。
5. 嵌套在别的目录下的 worktree 里，这些链接解析不到，工具把它们算作没检出。AIService 这类并列放置 worktree 的布局不受影响。

理由见[跨仓库链接决策](../decisions/cross-repo-links.md)。

## 13. 接入验收

- 新成员能从入口找到需求、原则、设计、源码和测试。
- 复制项目模板和完整 `scripts/wiki/` 到临时项目后，Agent 入口能找到同步文档与提交技能，技能的本地链接均可打开，无需回到源仓库读取其他文件。需要宿主原生发现时另行验证，不把 `AGENTS.md` 的按需入口当作原生发现已生效。
- Agent 能在局部修改中发现相关跨模块约束。
- 普通查询优先得到当前文档，历史仍可按需检索。
- 现行知识能够原位维护，完成计划能按原路径归档。
- 新建检查、真实暂存检查及独立模块检查有实际运行结果。
- 提交只改代码时能看到文档提醒，`doctor` 显示两个 Git 钩子已安装。
- 一项未改变文档所述契约、未达累计复核阈值的普通修复，只提交代码和测试，不更新状态页、不新增计划、不补复核 trailer，也能通过钩子。
- 文档开发流程已按共享基线迁移；旧流程中逐任务、逐提交的要求已逐条核对，重复或冲突已同步修改原入口与读取方，必要例外符合[共享流程与项目适配](../../scripts/wiki/workflow.md#共享流程与项目适配)。
- 同时使用执行套件时，根 `AGENTS.md` 能找到开发入口中的项目绑定；实际消费者沿绑定找到任务、执行记录、待处理项、验证和归档约定，没有另一套仍强制执行的默认路径。只核对文档而未运行套件时，明确记录此限制。
- 至少一条需求能从编号找到测试，需要设计或计划的工作还能找到相应文档，`check` 没有 `trace-unknown-ref` 错误。
- 写作与结构问题分别复核，不把脚本通过当作内容完全正确。

验收后，将本次接入的有效规则写回目标项目知识；已有计划保留验证记录与剩余事项，没有计划的工作在提交中记录依据和验证结果。后续升级工具时复核配置与规则变化，避免静默改变门禁强度。
