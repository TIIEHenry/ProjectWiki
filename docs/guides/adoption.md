# 接入 ProjectWiki

对应需求：PW-10。

本指南供接入项目的开发者与 Agent 使用。目标是建立能支持真实开发任务的最小文档体系。

## 1. 阅读 ProjectWiki 并调查目标项目

先读[设计原则](../principles/document-system.md)、[接入项目的目录](../design/document-model.md#接入项目的目录)、[开发流程](workflow.md)和[参考项目](../../demo/README.md)。

进入目标仓库后，检查现有 `AGENTS.md`、README、模块、文档、开发记录和历史目录。保留已有约束，找出当前权威页面、重复说明与仍有用途的旧材料。

不要把 ProjectWiki 自己的产品需求复制成目标项目需求。文档结构可以复用，业务内容必须依据目标项目实际情况编写。

## 2. 先建立两个真实阅读路径

选一项功能修改和一项维护问题，明确需要的需求、原则、设计、代码与测试。先用这两个任务检验目录与模板，避免一次建立大量空页。

每条路径应让读者明确目标、约束、实现入口和验证方式。增加一个反例：局部配置修改会影响另一个模块时，相关契约能否被找到。

## 3. 建立最小结构

参考 [`templates/project/`](../../templates/project/README.md)，按目标项目需要创建根 `docs/`、`dev/`、`archive/`。原有模块布局保持不变，单模块知识继续靠近源码。

一个新的、小型项目可以采用模板中的合并页面。内容增多后，再按需求、原则、设计和规范拆分。已有有效文档可以直接登记，不要求先改名或搬家。

使用模板前阅读[模板说明](../../templates/README.md)。复制单个文件时检查目标是否已存在，合并已有内容，不覆盖仓库现行规则。

**旧仓库的过渡表。** 已有大量文档、同一主题有好几篇，而这些文档又不能一次整理完时，先建一张"现行权威表"，例如 `docs/current-sources.md`。每个主题一行，写三列：主题、现行权威文档、不要再参考的旧文档。Agent 和新成员遇到同主题的多篇文档时，只读权威列。之后每归档一篇旧文档就删掉表里对应的一格，所有主题都只剩一份正文时，整张表也一起删除。这张表只用于过渡，不能变成长期维护的第二份导航。

**检查 AI 工具的输出位置。** 一些 Agent 技能会按自己的默认路径写计划或报告，例如写到 `docs/<工具名>/plans/`。接入时搜索 `docs/` 下由工具生成的目录，把内容移到 `dev/`；能改配置的工具改掉默认路径，不能改的在 `AGENTS.md` 里写明生成后移走。

**变更日志。** 项目已经有 `CHANGELOG.md` 时保留它，并在 `docs/INDEX.md` 里登记为用户可见变化的记录。有发布流程的项目，建议在发布脚本里检查当前版本是否已经写进变更日志，没写就停止发布。

**仍约束行为的决定。** 现有决策如果放在 `dev/decisions/`，把仍然约束当前行为的决定移到所属知识范围的 `docs/decisions/`。其中若有一份规定以后的决定也写在 `dev/`，用新的决策替代这条约定；知识和行动分开的结论可以保留。文件名写主题，不沿用全局顺序号。

**模块清单。** 用构建入口核对 `AGENTS.md` 和文档里的模块表。手写表会漏掉已经参与构建的模块。这项对账还要人工做，工具目前不读构建文件。

**包含路径的大小写。** `CLAUDE.md` 等文件里的包含路径必须与真实文件名大小写一致。区分大小写的系统不会把 `AGENTS.MD` 解析成 `AGENTS.md`。

## 4. 编写关键入口

`AGENTS.md` 直接写明项目目的、适用的硬规则、默认搜索范围与验证命令。详细理由可以链接出去，遵守关键规则不能依赖继续打开链接。

根 README 面向人介绍项目和入口。`docs/INDEX.md` 根据任务说明何时读哪篇文档。模块 README 说明职责、相关契约、源码和测试位置。

创建稳定知识时使用[写作规范](../standards/writing.md)：写清对象与条件，解释术语，删除 AI 套话、翻译腔和开发流水。全文读一遍，再运行结构检查。

## 5. 接入本地检查

将整个 `scripts/wiki/` 复制到目标仓库的合适位置，并登记自己的 `docs/wiki.json`。目录里的 `README.md`、`reference.md` 和 `formats.md` 要一起复制：目标项目的 Agent 按它们查命令、规则和固定写法，不需要再打开 ProjectWiki 仓库。配置路径相对 `--root` 指定的项目根目录。

配置至少列出知识根、过程根、归档根和入口，并按实际结构登记模块。小模块可以只登记 README；有独立文档目录时再填写模块 `docs`。根项目的检查应排除独立示例或子项目，再单独检查它们。检查工具不应依赖搜索时的忽略范围。

```bash
python3 scripts/wiki/wiki.py check --root .
python3 scripts/wiki/wiki.py doctor --root .
```

也可以先从 ProjectWiki 工具目录检查目标项目，无需立即复制脚本：

```bash
python3 /path/to/ProjectWiki/scripts/wiki/wiki.py check --root /path/to/target-project
```

这里的 `/path/to/` 是命令示例占位符，执行时替换成实际路径，不要把本机绝对路径写进目标项目的正文链接。

## 6. 设置默认搜索与文档创建检查

在目标仓库已有的 `.ignore` 中合并 `/archive/`。归档继续纳入 Git。接入旧布局时，将实际的嵌套历史目录登记为 `archive` 角色，并为这些目录补充精确的搜索忽略规则。

新归档默认使用已登记的根 `archive/`；采用其他名称时，在配置中用 `archive_root` 指定主目标。旧历史根仍参与分类和检查，但工具不推断旧布局与原路径的对应关系，需要按主题另行检索。

新建文档前执行以下命令，将路径替换为待建文件：

```bash
python3 scripts/wiki/wiki.py check-new docs/design/new-topic.md --root .
```

检查匹配主目标下的完整原相对路径。命中历史时返回警告，退出码仍为 `0`；阅读历史内容后判断是恢复、延续还是新主题。当前目标已存在则失败。检查不会把必要标准文件名永久禁用。暂存检查也会检查相对捕获 HEAD 新增的文档，提示同一索引快照中的对应历史。

## 7. 接入提交检查

首先让工作区检查通过。在 Git 仓库中暂存配置、正文和相关文件后，再检查实际暂存快照：

```bash
python3 scripts/wiki/wiki.py check --root . --staged
```

项目没有其他钩子时，复制 `scripts/wiki/hooks/` 并在每个 clone 执行一次 `git config core.hooksPath scripts/wiki/hooks`。已有钩子工具时，把 `check --staged` 加进现有 pre-commit、`remind --staged --message-file "$1"` 加进现有 commit-msg，不要覆盖原有配置。仓库里存在脚本不代表当前工作副本已经启用，运行 `doctor` 查看 `git_hooks` 的结果。配置里还没有 `remind` 时，commit-msg 输出警告 `remind-not-configured`，这次提交成功；阈值和拦截要等第 8 步写好 `remind` 才生效，见[提交时的文档提醒](../../scripts/wiki/reference.md#提交时的文档提醒)。

退出码 `0` 表示本次检查没有错误，可能仍有警告；`1` 表示发现错误；`2` 表示输入或执行条件不完整。钩子须将 `1` 和 `2` 都视为失败。没有 Git 仓库时只能运行工作区检查，不能据此报告提交门禁已通过。

用临时 Git 仓库验证一个反例：暂存区链接仍错误，工作区已修好，提交检查仍应失败。不要用未暂存的修复掩盖实际提交内容。

后续归档时先按[生命周期规则](../design/lifecycle.md)判断资格，工具不检查计划是否完成、决定是否失效。然后运行 `python3 scripts/wiki/wiki.py archive <原相对路径> --root .` 预览冲突和要改写的链接，确认后加 `--apply --expect <plan_sha256>` 执行。根目录已有 `archive/INDEX.md` 时，可以加 `--summary "<一行说明>"` 同时登记。

## 8. 设置文档同步提醒

在 `docs/wiki.json` 中加入 `remind`，把每组代码路径和描述它的文档登记为一个 `watch`，再设置提醒阈值；需要用户确认的需求、原则和决策文件写进 `ask_user`。字段说明见[配置与规则](../../scripts/wiki/reference.md#提交时的文档提醒)。默认可从 10 次提交或 300 行提醒、30 次提交拦截开始，按实际提醒频率调整。

提醒对所有 Agent 宿主通用，依靠三处：

1. Git `commit-msg` 钩子在每次提交时运行 `remind --staged`，提醒会出现在提交命令的输出里。
2. 目标项目的 `AGENTS.md` 写明：开始任务时运行 `python3 scripts/wiki/wiki.py remind --root .`；看到提醒必须处理，可以更新文档、在提交信息写 `Docs-Reviewed: <名称> <理由>`，或者把 `[user]` 类提醒报告给用户；不得用 `--no-verify` 跳过钩子。
3. 可选：宿主支持会话开始钩子时，让它运行同一条 `remind` 命令，把汇总注入上下文。例如 Kiro 可以创建 `SessionStart` 触发、命令为该命令的 hook；Claude Code 等宿主按各自文档配置。这一步只是让提醒更早出现，没有它前两条仍然生效。

用临时仓库验证：只改代码提交时出现 `docs-not-updated`；累计量超过 `block_at` 后继续改代码的提交失败；加上带理由的 `Docs-Reviewed` 后通过。

## 9. 给需求编号并接入追踪检查

把目标项目已确认的需求按[需求模板](../../templates/requirements.md)整理：每条一个带编号的标题、一行状态、带子编号的验收条件。已有 PRD 或需求清单时保留原编号，只补状态和验收子编号；编号不是 `APP-01` 这种格式时，在 `requirements.id_pattern` 里登记自己的格式，不要为了通过检查改编号。然后在 `docs/wiki.json` 加入 `requirements`，登记需求文件和测试文件的位置。

旧项目第一次运行通常会报出大量 `trace-no-design`、`trace-no-test`。先处理 `trace-unknown-ref` 这类错误，处理不完的错误可以记入存量基线；警告不会让检查失败，也不进基线，可以接入后再逐条为设计页补"对应需求："、为测试补验收编号。不要为了消除警告批量写入编号：引用要对应真实的覆盖关系。

## 10. 可选：核对记录与 OKF 导出

运维手册、外部事实、调查结论这类会过期的页面，在标题下写 `核对：agent:<名字>，YYYY-MM-DD。复核期限：YYYY-MM-DD。`，再在 `docs/wiki.json` 的 `verification.review_by_required` 里登记这些路径。需要人工把关的路径登记在 `verification.human_required`。格式见[文档模型](../design/document-model.md#核对记录与复核期限)。

需要把项目知识提供给支持 Open Knowledge Format 的工具时，运行 `python3 scripts/wiki/wiki.py export-okf --root . --out <项目外的空目录>`。导出不改变仓库里的写法，目录和规则见[配置与规则](../../scripts/wiki/reference.md#导出-okf)。

## 11. 登记验证命令与对账

把目标项目必须执行的测试和检查登记在 `docs/wiki.json` 的 `verify` 里，每条命令写成参数数组，必要时写运行目录和环境变量。之后计划的验证记录用 `python3 scripts/wiki/wiki.py verify --root .` 生成，Agent 不再手写命令结果和哈希。`AGENTS.md` 和开发规范里只写这一条命令，命令清单只在配置里维护一处。字段见[配置与规则](../../scripts/wiki/reference.md#验证记录)。

文档里有规则名、配置项、环境变量这类与代码一一对应的名单时，可以登记 `reconcile`，让 `check` 比较两边的名单。先在一处名单上试用，看误报能否用少量 `ignore` 排除；排除项比名单本身还多时，这份名单不适合用正则对账。字段见[配置与规则](../../scripts/wiki/reference.md#文档与代码对账)。

## 12. 接入验收

- 新成员能从入口找到需求、原则、设计、源码和测试。
- Agent 能在局部修改中发现相关跨模块约束。
- 普通查询优先得到当前文档，历史仍可按需检索。
- 现行知识能够原位维护，完成计划能按原路径归档。
- 新建检查、真实暂存检查及独立模块检查有实际运行结果。
- 提交只改代码时能看到文档提醒，`doctor` 显示两个 Git 钩子已安装。
- 至少一条需求能从编号找到设计、计划和测试，`check` 没有 `trace-unknown-ref` 错误。
- 写作与结构问题分别复核，不把脚本通过当作内容完全正确。

验收后，将本次接入的有效规则写回目标项目知识，保留计划中的验证记录与剩余事项。后续升级工具时复核配置与规则变化，避免静默改变门禁强度。
