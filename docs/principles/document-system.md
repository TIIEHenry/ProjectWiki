# 文档系统设计原则

对应需求：PW-03、PW-13、PW-15、PW-16、PW-26。

## 稳定知识与开发过程分开

`docs/` 描述项目当前的目标、边界、规则和设计。`dev/` 组织开发流程，记录计划、待决事项、执行、验证与交接。持续有效的重要决定保存在相应知识范围的 ADR 中。`archive/` 保存已结束的过程和整篇失去适用对象的内容。

已确认但尚未实现的需求仍属于知识。任务进度不能改变需求本身的效力；源码与需求不一致时，在对应计划或 `dev/inbox/` 中记录差距和处理依据。

## 先让人读懂

稳定知识面向需要理解项目的人。正文使用完整解释，交代对象、条件、行为和原因。Agent 能检索的字段、编号与目录是辅助结构，不能取代正文。

标题说明主题，摘要说明内容。导航说明何时需要阅读。避免把提交记录、阶段编号、内部简称和连续状态更新写进知识摘要。具体要求见[写作规范](../standards/writing.md)。

## 按任务逐层提供上下文

项目入口提供全局硬规则和任务导航；模块入口提供职责与相关契约；专题页提供细节；源码和测试用于确认行为。

开始修改前，开发者应能回答目标与验收、适用约束、实现位置和验证方法。信息不足时定向补读。跨模块契约应列出提供方与使用方，使局部修改能够发现相关影响。

入口预算同时考虑字符数、导航条目和必要约束。先用一项功能修改和一项维护任务检查阅读路径，再把适合项目的字符上限写入配置；超限时优先移出细节，保留必须直接可见的规则。条目数量由人工复核，当前工具只执行字符预算检查。只限制行数会让长行掩盖实际阅读负担。

会持续变长的登记表，例如延期缺口、问题清单和历史目录，应按编号或关键词搜索并只读命中的行，不整篇读入。入口要写明哪些文件属于这一类，以及该用什么关键词去查。

入口失效的迹象是：会话约定改成不要整篇阅读它，或者每次开工都必须通读一份长规范。曾出现约 200KB 的索引导航被禁止整篇阅读，另一个项目要求每次通读约 26KB 的文档规范。出现这些迹象时，把入口改回短导航，把会增长的登记表改成按编号检索。

## 关键规则直接可见

影响全项目修改、忽略后会导致错误的规则直接写在 `AGENTS.md`。详细规范可以解释背景、例外和操作步骤，但遵守关键规则不能依赖 Agent 继续打开链接。控件尺寸、调用顺序和局部实现约束放在模块文档，不堆进 `AGENTS.md`。

内联规则和详细正文保持一致。同一次规则变更需要审查两处；条款编号或链接存在只能证明结构关系，不能证明意思相同。

## 权威正文与受控摘要

同一条规则只指定一份权威正文。`AGENTS.md` 可以复述忽略后会直接导致错误的硬规则，但每条复述都链接回权威正文；模板和参考项目只保留执行所需的短摘要，不再复制完整解释。修改权威正文时，按链接和关键词检查受控摘要、模板和示例是否仍然一致。工具可以列出需要复核的链接关系，不能代替语义核对。

## 一份当前正文，多个导航入口

同一主题在同一适用范围和版本下指定一份当前正文。开发入口、维护入口和模块入口可以从不同任务链接它，无需各写一遍说明。

模块内部知识放在模块的 `docs/`，跨模块关系放在全局设计中。全局模块表直接指向模块入口，避免人工复制模块专题清单。

## 长期知识原位维护

需求、原则、`module-structure.md` 和当前接口契约持续原位更新，修订历史由 Git 保存。普通内容更新不触发整页归档。

归档适用于已结束的工作材料，或整篇已不再承担当前职责的文档。archive 中的同名文件不阻止新建标准文档，但需检查并明确两者关系。

文件名只承担导航提示。命名规则、占位模板、状态词和归档冲突的具体约定见[文档模型](../design/document-model.md#文件命名)；不要用全局编号、状态词、版本号或复杂 frontmatter 把文件名变成另一套状态系统。是否用日期前缀由项目决定，但日期只能表示一个不再改变的时间点，例如审查开始的日期，不能随进度改名。

## 检索范围与访问权限分开

日常搜索默认聚焦当前知识，减少历史全文干扰。Agent 可以按任务需要扩大到归档范围。

搜索忽略规则、当前知识索引和全量检查具有不同范围。生命周期与迁移检查仍须覆盖历史；搜索排除不能掩盖归档中的结构问题。

## 自动化保持明确边界

检查、生成、移动是不同操作。报告须说明输入快照、实际检查项和未覆盖部分。某项配置检查通过，不能据此声称整篇契约已经验证。

将目录位置、预算和规则放进共同配置，避免各脚本使用不同的范围。接入已有项目时可以登记存量问题，但不能通过比较告警总数掩盖新增问题。

## 规则分强弱，给项目留出调整空间

接入的项目规模、语言、已有文档和流程各不相同。规则写得太死，接入时要么被迫大改已有内容，要么为了通过检查去凑格式。所以规则分三层，每层的强度和调整方式不同。

| 层级 | 包括什么 | 能否调整 |
|---|---|---|
| 不变量 | 违反后工具的结论会失真或内容会丢失：不完整的检查不能报告为通过；暂存检查只读取捕获的 Git 索引；归档和新建不覆盖已有文件；现行文档的本地链接和锚点必须有效；同一范围内的需求编号、审查问题编号和当前文档身份不重复 | 固定为错误。旧仓库接入时只能用存量基线暂时接受已有问题，新问题照常失败 |
| 默认约定 | 目录位置、状态值、需求编号格式、文件命名、页面预算、提醒阈值、审查文件结构 | 工具给出默认值，项目在 `docs/wiki.json` 里按自己的结构调整 |
| 建议 | 写作风格、什么时候写决策记录、接入时启用哪些能力 | 只写在规范里，不做机器检查，由评审判断 |

默认约定里，审查的判定词和问题编号格式目前还不能配置；已有自己审查流程的项目可以把配置里的 `reviews` 设为空列表，审查检查就不会运行。

有些错误来自工具自身的限制，而不是文档本身的要求。例如新文档路径不能含空格，是因为归档还不能安全改写这类链接；工具能处理之后，这类规则应当降为默认约定。

调整默认约定时遵守三点：

- 已有内容优先登记，不为通过检查改写。已有的需求编号、目录和文件名，在配置里登记它们的格式和位置，不批量改名。
- 放宽要可见。调整写在配置里，并在提交信息中写明原因，评审能看到哪些默认约定被改过。
- 只在真实项目遇到默认约定不适用时增加配置项，不预先为假想的项目加开关。新增的检查先以警告上线，在实际项目上确认误报可以接受后再升为错误。

## 控制文档数量

能写成已有文件里的一节，就不新建文件。只有两种情况单独成文：这部分内容有自己的生命周期，需要单独排期、更新和归档；或者需要多人同时写，放在一起会互相冲突。

每做一步就新建一个文件，文件数会随轮次、参与者和模型成倍增长。一个参考项目的开发目录积累了四千多篇文档，其中两千篇是审查、审计和签收稿；一次审查 80 条问题，用了 43 个文件。轮次、模型和每次核对的日期应当写在正文里，不写进文件名；审查目录名里的开始日期只标出这是哪一次审查，不随轮次增加文件。目录可以在配置中设置文件数预算，超出时检查工具会提醒合并或归档；项目模板给计划、收件箱和审查目录设了默认预算。

一条一文件的登记方式，例如收件箱，必须同时规定每条怎样结束。只规定怎样新建、不规定怎样结束，文件数只会增长。

## 流程按影响展开

普通修复可以复用现有工作记录。出现重要取舍、跨模块契约变化、数据迁移或协作交接时，再增加相应计划和决策。

减少文件数量不能免除适用规则和验证。增加文件数量也不能代替实际分析。ADR、计划与路线图的分工见[开发流程](../guides/workflow.md)。
