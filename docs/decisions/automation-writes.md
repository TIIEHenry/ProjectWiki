# 决策：机械步骤由工具执行，判断仍由人或 Agent 做

状态：采用。范围：`scripts/wiki/wiki.py` 的写入命令、验证记录和文档对账，以及接入项目的 Agent 工作方式。

## 问题与约束

接入 ProjectWiki 的项目多数由 Agent 循环开发。工具如果只提供预览，移动文件、改链接和写验证记录都由 Agent 手工完成，容易出现两类问题：

- 归档需要多次调用：预览、移动、逐条改链接、补历史索引、再检查。工具在预览时已经算出了目的地和每个新链接。
- 验证记录可能在命令运行前被手写，数量、结果和文件哈希容易失真。

这两类步骤都可以由工具精确完成。由 Agent 手工做既多花 token，也会出错。

约束：`check` 是提交门禁，必须只读，相同输入给出相同结果；已有规则要求归档不覆盖历史；核对行、人工签收这类记录必须反映真实发生的核对。

## 决定与理由

可以从现有输入精确算出结果的步骤，由工具执行：

- `archive --apply --expect <plan_sha256>` 执行预览给出的归档计划，包括移动和改链接；`--summary` 同时在历史索引里加一行。计划哈希覆盖目的地、源内容和所有要改写的文件，预览之后任何一项变了都拒绝执行。目的地已存在时不覆盖。执行后自动运行 `check`。
- 归档执行先把所有改写内容写入临时文件；准备失败时不移动源文件，提交失败时尝试逆序回滚移动和改写，并报告强制终止可能留下的中间状态。
- `verify` 运行配置里登记的验证命令，把日期、Git 状态、文件哈希、每条命令的退出码和输出摘要写成一段 Markdown，计划直接引用这段输出。
- `index --write` 写生成目录。
- `reconcile` 让 `check` 比较文档和代码里的同一份名单，代码改了而文档没改时报错。

需要判断的事情，工具不代做：

- 核对行和复核期限续期。工具如果能自动续期，复核期限就失去了意义；循环里的 Agent 也会倾向于让检查变绿，而不是真的去核对。
- `human:` 签收、需求状态和采用决定。这些需要有人负责。
- 稳定知识的正文。工具可以比较名单、生成机器目录，说明文字仍由人或 Agent 写，再经过评审。

写入的边界：`check`、`remind`、`doctor`、`check-new` 和预览保持只读；Git 钩子只检查和提醒，不修改文件或暂存区。

## 替代方案

- **继续只提供预览。** 每次归档都要手工改链接，多花 token，链接也会漏改。没有采用。
- **在 Git 钩子里自动修复。** 提交时悄悄改文件，提交内容和作者看到的不一致，循环里也说不清差异从哪来。没有采用。
- **在 Markdown 里划出生成区域，由工具重写表格。** 文档里的表格通常还有人写的说明列，整段重写会冲掉这些内容。改为对账：表格仍由人写，工具只检查名单是否一致。
- **`verify` 通过 shell 运行命令。** 写法更灵活，但管道会吞掉前一条命令的退出码，也让配置里的命令更难审查。改为参数数组。

## 影响与退出条件

- 归档从多次手工操作变成两条命令：预览，然后带哈希执行。改写的链接仍指向同一篇内容；现行入口页的链接会被改进归档时给出警告，要不要改为链接当前文档由人判断。
- 工具找不到登记文档以外的引用，例如代码注释和排除目录里的文件。这部分仍需按关键词搜索。
- 提交阶段进程被强制终止时，工具不能保证自动清理临时文件或恢复所有中间状态。
- `verify` 会运行仓库配置里的命令，信任程度与运行项目自己的测试相同。
- 对账用正则匹配文字，不理解代码结构，误报靠 `ignore` 排除。如果某个接入项目的 `ignore` 列表比名单本身还长，说明这种名单不适合用正则对账，应当撤掉这一项配置。
- 如果日后需要片段归档或批量迁移，另写需求和决策，不扩大本决定的范围。
