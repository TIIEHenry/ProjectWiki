# 决策：需求用正文编号贯穿设计、计划和测试，由工具检查

状态：采用。范围：ProjectWiki 与接入项目的需求文件、设计文档、计划和测试。

## 问题与约束

需求、设计、计划和验证虽然分开存放，彼此却只靠文字描述关联。实际维护中会出现：

- 需求编号 `PW-` 只出现在需求文件和一份计划里，没有设计文档写明自己满足哪条需求，测试也一条都没引用；
- 当天新增的提交提醒、状态行、存量基线、审查检查等功能都没有对应的需求条目，是先写了实现；
- 验收方式写成"读者能找到……"这类描述，没法写成测试，也看不出哪些已经实现、哪些已经验证。

约束：不引入专用格式或第三方库；需求文件要让人直接读懂；普通小修复不能因此多出一套手续。

## 决定与理由

需求文件里每条需求是一个标题，标题以编号开头；标题下第一行写状态；验收条件逐条列出，每条有子编号：

```markdown
### PW-11 提交时提醒同步文档

状态：已验证。

在一次提交里改了某组代码、却没有改对应文档时，提交输出中给出提醒。

- PW-11.1 当暂存的改动包含已登记的代码路径、但不包含对应文档时，`remind --staged` 输出 `docs-not-updated`。
- PW-11.2 当提交信息带有写明理由的 `Docs-Reviewed` 时，累计计数清零。

证据：[行为测试](../../tests/test_wiki.py)。
```

需求状态有五种：提出、已接受、已实现、已验证、已废止。不能由命令证明的验收条件在末尾标"（人工验证）"，并另写一行 `验收核对：PW-11.1，agent:<名字>，YYYY-MM-DD。`。核对行说明谁在什么时候做过这项人工检查，不代表语义一致。

下游用编号引用需求：设计文档写"对应需求：PW-11"；计划写"覆盖需求：PW-11"；测试在说明文字里写上验收编号，例如 `PW-11.1`。

工具在 `check` 里检查：

1. 引用了不存在的需求编号或验收编号时报错。
2. 已接受及之后状态的需求，没有任何设计文档或模块文档引用时警告。
3. 已实现或已验证的需求，每条验收编号都要至少被一个测试引用，否则警告；标了人工验证的条目由验收核对记录代替测试。核对记录写在其他条目下时另给警告，不代替测试，因为能写测试的条目不应靠一句"已核对"通过。
4. 已验证的需求需要一行带链接的"证据"，否则警告。
5. 计划没有"覆盖需求："一行时警告。维护类工作可以写"覆盖需求：无"，并说明原因。

这套写法和[审查记录](../design/document-model.md#审查记录)里"编号贯穿全程、方案写'覆盖问题'"是同一种机制，工具和读者只需要学一次。

## 替代方案

- **每条需求一个文件，或者用 YAML 描述。** 机器读取方便，但需求文件会碎成几十个小文件，违背"能写成一节就不新建文件"的原则。没有采用。
- **单独维护一张追踪矩阵。** 矩阵和需求、设计、测试分开存放，任何一边改了都要回来同步，会产生另一份容易过时的正文。没有采用。
- **规定 EARS 句式，例如"当……时，系统应当……"。** 句式有助于把验收写成可测试的形式，可以在写作时作为参考，但工具不强制检查句式。

## 影响与退出条件

- 需求文件的写法变得更固定。普通修复不需要新建需求，只在提交或计划里引用已有编号即可。
- 工具只能确认编号引用存在，不能判断测试是否真的覆盖了验收条件，也不能判断设计是否真的满足需求。这些仍需评审。
- 如果大多数接入项目已经使用其他需求管理系统，可以把编号来源改成从外部导出的清单，再评估是否替代本决定。
