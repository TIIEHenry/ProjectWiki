# 决策：用正文核对行记录信任与新鲜度，OKF 只作为导出格式

状态：采用。范围：ProjectWiki 与接入项目的知识页、审查核对表和导出工具。

## 问题与约束

ProjectWiki 能检查审查问题是否由非作者核对、需求是否有证据，但知识页没有"谁在什么时候核对过、什么时候该再核对"的记录；核对人只是普通文字，工具分不清人和 Agent。

Google 发布的 [Open Knowledge Format（OKF）](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md) v0.2 把这两件事做成了 frontmatter 字段：`verified` 记录核对事件，按核对人是否带 `human:` 前缀划分可信等级；`stale_after` 写一个绝对的过期时间；`status` 取 draft、stable、deprecated。

约束：ProjectWiki 已经决定不强制 frontmatter（见[状态行决策](status-line.md)）；OKF 一个概念一个文件、推荐以 `/` 开头的链接、用 `log.md` 记历史，这三点都和现有规则冲突；OKF 的版本还在快速变化。

## 决定与理由

知识页在一级标题下、第一个二级标题之前写一行核对记录，需要时再写复核期限：

```markdown
# 标题校验失败的处理

核对：agent:kiro，2026-10-28；human:clarence，2026-11-02。复核期限：2027-04-28。
```

- 核对人写成 `human:<名字>` 或 `agent:<名字>`。审查核对表的核对人、问题作者也用同一写法。
- 工具据此分出三个信任级别：没有核对行是未核对；只有 Agent 核对过；有人工核对。
- 复核期限是绝对日期。到期提醒放在 `remind` 里，`check` 只检查格式，因此 `check` 的结果不会随日期变化。
- 配置可以要求某些路径必须写复核期限，或者必须有人工核对。

需要和 OKF 工具互通时，用 `export-okf` 把现行知识导出成 bundle：在每篇前面加 frontmatter，状态、核对行和复核期限分别映射成 `status`、`verified` 和 `stale_after`。仓库里的写法不变。

## 替代方案

- **直接采用 OKF 作为写作格式。** 要给每篇文档加 frontmatter，把需求条目和审查问题拆成一个概念一个文件，还要改链接写法。这与状态行决策和"能写成一节就不新建文件"的原则冲突，而且规范版本还在变。没有采用。
- **只借鉴字段，不提供导出。** 写法一致的好处保留了，但别的工具读不了。导出的成本很低，所以一并提供。
- **按修改日期判断是否过期。** 参考项目里这类日期提示攒了上千条，没人处理；改过不代表核对过。没有采用。

## 影响与退出条件

- 知识页多了一行可选的核对记录。没写不报错；只有配置要求的路径才检查。
- 工具只能检查 `human:` 前缀写得对不对，无法确认真的是人写的。规则要求 Agent 不得把自己写成 `human:`，这一条只能靠评审和提交记录核对。
- 复核期限设了却没人续期，到期后会集中提醒。只给确实会过期的页面设期限，核对时一并续期。
- OKF 发布 v1.0 后，按新版本重新评估导出映射。如果大多数接入项目需要在仓库里直接维护 OKF，再评估是否替代本决定。
