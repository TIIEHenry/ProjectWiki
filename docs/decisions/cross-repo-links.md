# 决策：跨仓库链接用相对路径，登记相邻仓库后检查

状态：当前有效。范围：ProjectWiki 工具与接入项目里指向其他仓库的链接。

## 问题与约束

一个系统可以由几个仓库并列检出组成。接入 ProjectWiki 的 AIService 有 7 个这样的仓库，它们的构建本来就要求并列检出：`settings.gradle` 用 `includeBuild('../FlymeAIEngine')` 引入相邻仓库，同步脚本从 `$ROOT/../FlymeAIEngine` 找副本。

工具只认一个项目根，越出项目根的链接在现行文档里报 `unsupported-link`。项目只能绕开它，结果是：

- 19 条跨仓库相对链接里，7 条能打开，11 条少写了一层 `../`，1 条的目标已经不存在。工具没有发现其中任何一条：一个仓库把它们冻结进了存量基线，另一个仓库的相关文件根本没登记。
- 另一些项目把外部路径写成行内代码，不再是链接，也就无法检查。
- 同一份契约在几个仓库里分别写，已经互相矛盾，而使用方没有可以链接的目标。

约束：不引入新的链接语法，编辑器和网页渲染器照常显示；单仓库项目不受影响；仓库不一定全部检出，持续集成通常只检出一个。

## 决定与理由

1. **跨仓库链接写相对路径，在配置里用 `repos` 登记目标仓库。** 登记项是仓库名和相对项目根的路径，路径必须在项目根以外。
2. **目标仓库已检出时，检查目标文件（区分大小写）和锚点。** 没检出时不判失败，每个仓库给一条警告 `repo-not-checked-out`，写出有多少条链接没检查，报告的 `coverage.repos` 列出每个仓库的状态。需要强制时加 `check --require-repos`，仓库读不到就报告 incomplete。
3. **没初始化的子模块和没检出的相邻仓库同样处理。** 子模块是 Git 索引里的一个提交指针，不需要登记。
4. **暂存检查读登记仓库在检查开始时的 HEAD 提交，不读它的工作区。** 报告写出这个提交。工作区检查读目标仓库的工作区，用于编辑反馈。
5. **断链提示给出改法。** 多写或少写一层 `../` 就能打开时，在提示里写出改后的链接。提示不进基线指纹，已有基线继续有效。
6. **报告列出没被登记、因而没被检查的 Markdown。**

第 4 条改写了一条不变量。以前是"暂存检查只读取捕获的 Git 索引"，现在是"暂存检查只读取捕获的 Git 索引，以及登记仓库在检查开始时的 HEAD 提交"。理由是：结果仍然可以复现，相同的索引加相同的相邻仓库提交，结论相同；工作区里的未提交修改既不会掩盖问题，也不会让检查失败。

## 替代方案

- **链接写托管网址，在配置里映射到本地目录。** 网页上能打开，但一个仓库往往有两三个远程（本机的 AIService 同时有 GitHub 和公司内部远程），远程名与目录名也对不上，选不出唯一的网址；网址里还要写死分支。没有采用。接入项目真有在网页上浏览跨仓库链接的需求时再加。
- **建共享契约仓库。** 是项目自己的组织决定，工具在两种布局下都能用。没有采用，也不阻止。
- **只写仓库名，不加链接。** 现状。矛盾出现了也没人发现。没有采用。
- **暂存检查完全不看跨仓库链接。** 不变量不用改，但坏链接在提交时永远发现不了，现有的 11 条就是这样提交进去的。没有采用。
- **暂存检查读相邻仓库的工作区。** 能看到对方未提交的修改，但结果不可重复，同一个索引在不同时间得到不同结论。没有采用。
- **提供路径覆盖，让嵌套的 worktree 也能解析。** 覆盖只能让工具的判断正确，编辑器里的跳转仍然打不开，两边结论会不一致。没有采用。

## 影响与退出条件

- 单仓库项目不写 `repos`，行为不变。多出的是两条通用警告：`unregistered-markdown`（有 Markdown 不在任何登记范围内）和没初始化的子模块的 `repo-not-checked-out`。
- 链接要求相邻仓库按登记的相对位置检出。嵌套在别的目录下的 worktree（例如 `项目-WorkTrees/A`）里，这些链接解析不到，报告写"没检出"。
- 提供方改了契约页、还没提交时，使用方新加的指向新锚点的链接在暂存检查里会失败。先提交提供方，符合"契约由提供方写正文"。
- 归档只改本仓库里的链接。提供方通常不登记它的使用方，所以归档提供方文档时看不到大部分跨仓库入链。
- 提供方改了契约时提醒使用方，以及读目标仓库自己的配置判断目标是否已被替代，都还没做，见[待办](../../TODO.md)。
- 如果以后多数项目需要在网页上浏览跨仓库链接，再评估托管网址映射。
