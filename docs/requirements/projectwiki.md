# ProjectWiki 需求

## 使用者与场景

ProjectWiki 面向需要维护项目知识的开发团队，以及在同一仓库中工作的编码 Agent。接入项目可以是单模块工具，也可以由多种构建系统组成。

主要场景包括：新成员理解项目、Agent 定位修改范围、开发者维护接口与设计、协作者接续任务，以及维护者追溯历史决定。

## 如何阅读本文件

每条需求是一个三级标题，以编号开头，标题下第一行是状态，验收条件逐条列出、各带子编号。不能由命令证明的验收标"（人工验证）"并附验收核对记录。测试在说明文字里写验收编号；需要设计或计划时，分别用"对应需求："和"覆盖需求："引用编号。写法见[工具读取的写法](../../scripts/wiki/formats.md#需求条目)，理由见[需求追踪决策](../decisions/requirement-traceability.md)。

### PW-09 文档检查与实际接入可验证

状态：已验证。

- PW-09.1 相对链接按引用所在文件解析，检查精确大小写，不回退到仓库根目录；支持内联、引用式链接和图片，忽略代码块。
- PW-09.2 检查锚点，包括重复标题、中文标题和显式 HTML 锚点。
- PW-09.3 暂存检查只读取捕获的 Git 索引，以及登记的相邻仓库（PW-27）在检查开始时的 HEAD 提交；工作区里的修复、未跟踪文件和未暂存的配置不影响结果。
- PW-09.4 没有 Git、配置无效、必需输入缺失或索引有冲突时，报告 incomplete 并返回退出码 2。
- PW-09.5 现行页不能通过声明归档角色降低检查级别；现行页的相对链接越出项目根时报错，历史页只警告。
- PW-09.6 `doctor` 不声称已经验证任意钩子，能报告 ProjectWiki 钩子是否安装。
- PW-09.7 相同输入生成相同的索引，检查命令不写文件。
- PW-09.8 配置顶层、`remind` 和 `remind.watch` 出现未知字段时报告 incomplete，退出码为 2。例如顶层写成 `dir_budget`、`remind` 里写成 `plan_stale_day`，或 watch 条目多写 `doc`。
- PW-09.9 脚注定义 `[^名称]: …` 不登记为引用式链接，脚注正文不会被当成链接目标；脚注正文里的普通链接照常检查。
- PW-09.10 工作区检查跳过 Git 忽略的未跟踪文件和目录，已跟踪的文件不受影响；不在 Git 工作区里时读取全部文件，报告的 `coverage.git_ignored` 写明是否应用了忽略规则。
- PW-09.11 多写或少写一层 `../` 就能打开的断链，消息里写出改后的链接，保留锚点；没有能打开的改法时不给提示。提示不进基线指纹，写在提示之前的基线继续有效。
- PW-09.12 不在任何登记的根、模块、页面或入口里的 Markdown 不被检查，`check` 为此给出一条警告 `unregistered-markdown`，报告的 `coverage.unregistered_markdown` 写出数量和前 20 个路径；排除或登记后消失。已作为未登记 `docs/` 目录报错的文件不重复计入。
- PW-09.13 指向没初始化的子模块里的链接不报断链，每个子模块给一条 `repo-not-checked-out` 警告并写出链接数；子模块初始化后照常检查。暂存检查不读子模块的文件。

证据：[行为测试](../../tests/test_wiki.py)。

### PW-11 提交时提醒同步文档

状态：已验证。

Agent 开发时频繁提交。提醒挂在 Git 提交上，对所有 Agent 宿主通用。

- PW-11.1 暂存的改动包含已登记的代码路径、但不包含对应文档且没有复核 trailer 时，`remind --staged` 输出带 `[info]` 的 `docs-not-updated`，不拦截提交；未达累计阈值时不要求复核或写 trailer。已知正文失实时仍须当次更新。
- PW-11.2 改动对应文档，或在提交信息里写带理由的 `Docs-Reviewed` 后，累计计数清零；没有理由的 trailer 不清零。
- PW-11.3 累计量达到 `threshold` 后，给出 `[agent]` 提醒要求核对文档，更新正文或写带理由的复核 trailer；达到 `block_at` 后，只有继续改代码且未复核的提交会失败。
- PW-11.4 不带 `--staged` 的汇总模式只提醒，不返回失败。
- PW-11.5 改动决策记录时列出仍链接它、但本次未改动的现行文档；项目配置了 `ask_user` 时，改动其中的需求、原则或决策文件才提醒先向用户确认。
- PW-11.6 安装仓库附带的 Git 钩子后，结构错误阻止提交，只改代码的提交输出提醒。
- PW-11.7 没有 Git 时报告 incomplete。配置里没有 `remind` 时，`remind` 和 commit-msg 钩子给出警告 `remind-not-configured`，退出码为 0，提交继续完成。
- PW-11.8 状态为执行中、长期没有提交的计划，以及已结束仍留在 `dev/` 的计划或审查，会被提醒。
- PW-11.9 `remind --staged` 的改动文件和行数来自启动时捕获的索引对象与 HEAD 树，不在运行期间重新读取实时索引；行数只用于提醒阈值，报告写明这一近似限制。
- PW-11.10 本仓库的提醒配置把规范正文变更与模板、demo 和入口摘要的核对关联起来；只改规范正文而没有同步这些位置时，`remind --staged` 给出 `docs-not-updated`。（人工验证）
  验收核对：PW-11.10，agent:codex，2026-10-30。
- PW-11.11 索引里有符号链接或子模块时，`remind --staged` 照常完成，这些路径计为改动但不计行数；两边对象 ID 相同的路径不读取内容。
- PW-11.12 暂存的 Markdown 文件相对 HEAD 新增了写着 `human:<名字>` 的行时，`remind --staged` 给出 `[user]` 提醒 `human-claim-added` 并列出名字；已有的行、代码块和行内代码里的示例、`human:<名字>` 这类占位写法不提醒。
- PW-11.13 待处理项（默认 `dev/inbox/*/*.md`）状态是待分诊且超过 `plan_stale_days` 天没有提交时提醒 `inbox-stale`；状态已完成却仍在 `dev/` 时提醒 `inbox-finished-not-archived`；没有可识别的状态行时提醒 `inbox-no-status`。收件箱的 `README.md` 不检查。

证据：[行为测试](../../tests/test_wiki.py)。

### PW-12 计划与决策的状态可被工具识别

状态：已验证。

- PW-12.1 工具读取一级标题下第一行的 `状态：<值>。` 或 `Status: <value>.`，代码块中的内容不算。
- PW-12.2 入口页链接到被替代或废止的文档时报错，其他现行页面这样链接时警告。
- PW-12.3 决策记录之间的互相引用、指向归档目录的链接不触发上一条。
- PW-12.4 计划或决策缺少状态行、状态值无法识别时警告；项目可以在配置中补充状态值。
- PW-12.5 每个状态类别默认只识别一个中文值和一个英文值；项目自己的同义状态通过 `status_values` 配置，不继续扩大工具内置值表。（人工验证）
  验收核对：PW-12.5，agent:codex，2026-10-29。
- PW-12.6 配置 `status_frontmatter` 登记一个 frontmatter 字段名后，没有状态行的计划和决策记录从这个字段取状态，取值经 `status_values` 归类；不登记时不读 frontmatter。字段名不是单个标识符时报告 incomplete。
- PW-12.7 登记了 `status_frontmatter` 且状态行和字段都写了时，以状态行为准；两者类别不同时警告 `status-mismatch`，字段值无法识别时警告 `status-unknown`。

证据：[行为测试](../../tests/test_wiki.py)；[状态行决策](../decisions/status-line.md)。

### PW-13 旧仓库可以先接入、再逐步清理

状态：已验证。

- PW-13.1 存量基线中的已知错误不再导致失败，新错误照常失败；在同一文件中插入内容使行号变化，不会产生新的问题指纹。
- PW-13.2 基线中已经修好的条目会被提示删除，让基线只减不增。

### PW-41 提醒真正接上钩子

状态：已实现。

多数接入项目开工时运行 `remind`，却没装 Git 钩子，提交时的检查和提醒都没生效；配置还没提交的项目被暂存检查拦住，只能自己写脚本绕开；`Docs-Reviewed` 写错组名又被静默接受。`remind` 应当在这三处给出可操作的提醒，而不是放过或拦死。

- PW-41.2 `remind --staged`（运行在钩子里）不检查钩子；不是 Git 工作区，或钩子目录无法按 ProjectWiki 钩子识别（状态 unknown）时，不给 `hooks-not-installed`。配置里没有 `remind` 时仍然给出这条钩子提醒。

- PW-41.4 配置在 HEAD 里有、索引里被删除时，`check --staged` 仍报 incomplete、退出码为 2；配置在索引里（含这次新增）走正常检查。
- PW-41.5 `remind --staged --message-file` 读到的 `Docs-Reviewed` 名字不是任何 `remind.watch` 的 `name` 时，给出 `[agent]` 警告 `review-trailer-unknown-group`，列出已配置的组名，这个名字不清零计数；一行里多个名字时只对不存在的告警，存在的照常清零；`review-trailer-incomplete` 行为不变。

### PW-42 提醒计数不被接入提交和机械改动清零

- PW-42.3 配置了 `adopted_at` 时，`adopted_at` 指向的提交也当作接入提交。
- PW-42.4 配置文件从没提交过时没有接入提交，`remind` 的计数行为和过去一致。
- PW-42.5 一次提交里对 `watch.docs` 文件只改了 Markdown 链接目标（链接文字不变）时，不让该组清零；代码块和行内代码里的链接写法按正文判断。
- PW-42.6 一次提交里对 `watch.docs` 文件只改了 frontmatter 的 `updated`、`created`、`date`、`status`、`phase` 键值时，不让该组清零；正文中同名普通字段及非状态行的 `Status:` 或 `状态：` 文字的改动算实质改动。
- PW-42.7 对 `watch.docs` 文件做纯重命名或移动（忽略链接、机械字段、状态行差别后内容相同）时，不让该组清零。
- PW-42.8 对 `watch.docs` 文件改了正文（包括改变正文顺序）时，该组清零；项目根位于 Git 仓库子目录时，历史路径也相对项目根判断。
- PW-42.9 `remind --staged` 按捕获的 HEAD 与索引判断暂存的文档改动：纯移动不清零，只改链接不清零也不消除 `docs-not-updated`，改正文或新增副本清零。
- PW-42.10 `plan-stale` 和 `inbox-stale` 的天数从最后一次实质改动算起，跳过接入提交和只改链接或机械字段的提交。
- PW-42.11 计划正文的 `状态：` 或 `Status:` 行改动在天数计算里算实质改动，重新确认状态后计划不再判为过期；frontmatter 的 `status` 字段仍是机械字段。
- PW-42.12 判断实质改动的函数只有一处，`history_debt` 和 `days_since_commit` 共用，`状态：` 行是否算实质由参数区分。
- PW-42.13 同一 Wiki 实例只查询一次接入提交历史，空结果也复用；不同实例独立查询。
- PW-42.14 判断一次历史提交的文档改动时，批量读取所需对象；文档数量增加不逐个启动 Git 读取进程。
- PW-42.15 提醒并发读取需要计算过期天数的计划和待处理项，最多同时处理 8 个文件；每个文件仍沿用各自最近 30 次提交的扫描，观察组仍最多扫描 2000 次提交。
- PW-42.16 历史遍历保留分支提交；合并文本按 Git combined 差异的全父列新增或删除判断，不重复计算从各父提交继承或拼合的内容，也不推断冲突解决意图；观察组和过期天数使用相同合并判据。二进制或特殊文件类型的合并修改计入提交数、行数为零。链接目标识别与 Markdown 解析一致，frontmatter 只将顶层指定字段视为机械字段。

### PW-43 计划的整个生命周期都受提醒

状态：已实现。

`plan-stale` 只盯执行中的计划，草案和阻塞的计划无论搁置多久都不提醒，提示语却建议"标成阻塞"；阻塞的计划没有地方记录原因；计划误用决策记录的"当前有效"状态来避开归档提醒，工具不报。

- PW-43.1 状态是草案或阻塞的计划，超过 `remind.plan_idle_days`（正整数，默认 60）天没有实质改动时，`remind` 报 `plan-idle`，以 `[agent]` 开头，提示决定开始做、取消或写明仍在等什么；天数用 `days_since_commit` 计算，已有的 `plan-stale` 行为不变。
- PW-43.2 配置 `remind.plan_idle_days` 为非正整数或非整数时，报配置错误；不配置时默认 60。
- PW-43.3 接入起点之前的旧计划，`plan-idle` 并入 `legacy-lifecycle` 汇总，不逐篇报。
- PW-43.4 计划状态是阻塞但状态行里没有原因（或原因为空）时，`check` 报 `plan-blocked-no-reason`；状态行写了 `原因：<内容>。`（英文 `Reason:`）时不报。接入起点之前的旧文件不报。
- PW-43.5 计划状态是当前有效时，`check` 报 `plan-status-current`；frontmatter 经 `status_values` 映射成 current 的也报。接入起点之前的旧文件不报。
- PW-43.6 `remind` 列出阻塞的计划时，一并显示状态行里的原因；没写原因的标为未写。

### PW-44 限制页面与行的大小，发现重复入口，给其他过程目录预算

状态：已实现。

会持续增长的登记表和状态历史如果没有大小上限，单篇会膨胀到几 MB、单行塞进几十万字符，按关键词检索命中一行就等于读进整篇；两份逐字相同的入口文件靠人工同步维持一致；`dev/` 下 roadmap、reports、iterations 等子目录没有任何文件数预算。

- PW-44.1 非归档文档的字符数超过 `size_limits.page_chars`（默认 100000）、且没有登记自己的 `max_chars` 时，`check` 警告 `page-oversized`；不超过时不报。
- PW-44.2 页面登记了 `max_chars` 时，由 `page-budget` 按登记值判断，不再报 `page-oversized`。
- PW-44.3 文档里有行超过 `size_limits.line_chars`（默认 10000）时，每篇报一次 `line-oversized`，消息写出第一处超长行的行号、字符数和这篇超长行的总数。
- PW-44.4 `size_limits` 的 `page_chars`、`line_chars` 可分别调整上限，三个字段都可省略。
- PW-44.5 命中 `size_limits.ignore` 路径模式的文档，`page-oversized` 和 `line-oversized` 都不报。
- PW-44.6 归档角色的文档不报 `page-oversized` 和 `line-oversized`。
- PW-44.7 接入起点之前的存量文件照常报这两条规则，使存量大文件被看见。
- PW-44.8 `size_limits` 的未知字段、非正整数的 `page_chars` 或 `line_chars`、非路径模式数组的 `ignore` 都报 incomplete。
- PW-44.9 同一目录里 `AGENTS.md` 与 `CLAUDE.md` 都存在、去掉首尾空白后逐字相同、长度超过 200 个字符时，警告 `entry-duplicate`，建议保留一份、另一份改成一行 `@AGENTS.md` 导入。
- PW-44.10 两份入口内容不同、长度不超过 200 字符、或其中一份已是 `@AGENTS.md` 导入时，不报 `entry-duplicate`。
- PW-44.11 一个目录命中多个 `dir_budgets` 模式时，按最长（最具体）的模式判断，只报一次；`dev/*` 给 `dev/` 下其他子目录兜底预算。

### PW-45 把放错位置的文档搬到任意登记位置

状态：已实现。

放错位置的现行内容（留在 `dev/decisions` 的决策、在 `dev/plans/` 下的需求、`docs/modules/` 镜像目录、工具生成的成批文件）需要搬到正确的登记位置，而不是只能进归档。`archive` 已经有预览、计划哈希、入链出链改写、回滚和执行后 `check`，`move` 复用同一套核心，只是目的地由调用方指定。

- PW-45.1 `move <源> <目标>` 不带选项时只预览：列出要移动的文件、`source_sha256` 和 `plan_sha256`，以及要改写的入链和出链，不写任何文件。源可以是一份文档或一个目录，目录整体移动。
- PW-45.2 `move --apply --expect <plan_sha256>` 在哈希一致时移动文件、改写入链和出链、运行一次 `check` 并在 `after_check` 报告；入链是别的登记文档指向被移动文件的链接，出链是被移动文件里指向外部的链接。
- PW-45.3 计划哈希与 `--expect` 不一致时拒绝执行，不写文件。
- PW-45.4 目标已存在（包括空目录）时拒绝执行，不覆盖也不自动编号。
- PW-45.5 执行阶段失败时与 `archive` 一样只回滚本次完成的步骤，不覆盖其他写入者的文件；回滚不完整时报告已完成的写入和需要处理的问题。
- PW-45.6 目标不在项目根内，或不在任何已登记的根（knowledge、process、archive）或模块文档目录之下时，报 `move-destination-outside` 并拒绝。
- PW-45.7 源是配置文件、基线文件、生成目录里的文件或历史索引，或者目录包含这些受保护路径时，`move` 和 `archive` 报 `move-source-protected` 并拒绝。
- PW-45.8 源不存在、源与目标相同，或目标在源目录内部时，报 `move-invalid` 并拒绝；`archive` 的目标也不能在源目录内部。
- PW-45.9 目标文件名与源文件名相同、只换目录时不做新建命名检查；改了文件名时按新建命名规则检查，路径含空格、`#`、`%`、括号时报 `name-unsafe-character`。
- PW-45.10 目标在归档根里时报 `move-use-archive`，提示改用 `archive`；从归档根里把文档搬出来（恢复）用 `move` 允许。
- PW-45.11 `move` 和 `archive` 在预览与执行前检查源、目标和改写路径，路径中有符号链接或越出项目根时报 `archive-unsafe-path` 并拒绝。
- PW-45.12 搬迁已写入但执行后的检查无法运行时，报告检查未完成和已完成的写入。

### PW-27 多个仓库的文档可以互相链接

状态：已验证。

一个系统可以由几个并列检出的仓库组成。跨仓库的链接写相对路径，在配置里登记目标仓库；仓库不一定全部检出。

- PW-27.1 登记的仓库已检出时，指向它的链接检查目标文件或目录是否存在（区分大小写）和锚点，错误的级别与仓库内链接相同；报告的 `coverage.repos` 写出状态、读取方式和检查的链接数。
- PW-27.2 只读被链接到的文件；指向仓库以外的符号链接不跟随，按目标不存在处理。
- PW-27.3 越出项目根、又不在登记仓库里的链接，或在项目根内少写、多写了 `../` 的链接，消息里写出能打开的改法。
- PW-27.4 登记的仓库没检出（目录不存在或为空）时，指向它的链接不报错，每个仓库给一条 `repo-not-checked-out` 警告，写出未检查的链接数；`check --require-repos` 在任何登记仓库读不到时报告 incomplete。
- PW-27.5 暂存检查读登记仓库在检查开始时的 HEAD 提交，不读它的工作区，报告写出这个提交；目录存在但没有 HEAD 提交时按没检出处理。
- PW-27.6 `repos` 的登记项必须有唯一名称和在项目根以外的相对路径，路径不能相同或互相包含；写错时报告 incomplete。不写 `repos` 的项目，报告里没有仓库覆盖信息，行为不变。

证据：[行为测试](../../tests/test_wiki.py)；[跨仓库链接决策](../decisions/cross-repo-links.md)。

## 质量要求

文档使用具体、清楚的技术语言。编写者需要删除无信息量的铺垫、翻译腔和未定义的内部行话。机械检查只辅助发现问题，文风结论仍需阅读全文。

工具保持本地可运行。`check`、`remind`、`doctor`、`check-new` 和归档预览只读。写文件的只有 `archive --apply`、`index --write` 和 `export-okf`，都先核对目标状态，不静默覆盖内容；`verify` 只运行配置里登记的命令。不得把不完整的检查报告为通过。

`check` 的耗时随文档总长度和链接数线性增长，同一篇文档的链接只解析一次。几千篇文档、单篇几 MB 的仓库也要能在提交钩子里运行。

核对行、复核期限续期、人工签收、需求状态和稳定知识的正文由人或 Agent 写，工具不自动生成。
