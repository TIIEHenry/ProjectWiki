# ProjectWiki 需求

## 使用者与场景

ProjectWiki 面向需要维护项目知识的开发团队，以及在同一仓库中工作的编码 Agent。接入项目可以是单模块工具，也可以由多种构建系统组成。

主要场景包括：新成员理解项目、Agent 定位修改范围、开发者维护接口与设计、协作者接续任务，以及维护者追溯历史决定。

## 如何阅读本文件

每条需求是一个三级标题，以编号开头，标题下第一行是状态，验收条件逐条列出、各带子编号。不能由命令证明的验收标"（人工验证）"并附验收核对记录。设计文档用"对应需求："引用编号，计划用"覆盖需求："，测试在说明文字里写验收编号。写法见[工具读取的写法](../../scripts/wiki/formats.md#需求条目)，理由见[需求追踪决策](../decisions/requirement-traceability.md)。

### PW-09 文档检查与实际接入可验证

状态：已验证。

- PW-09.1 相对链接按引用所在文件解析，检查精确大小写，不回退到仓库根目录；支持内联、引用式链接和图片，忽略代码块。

- PW-09.3 暂存检查只读取捕获的 Git 索引；工作区里的修复、未跟踪文件和未暂存的配置不影响结果。

- PW-09.5 现行页不能通过声明归档角色降低检查级别；现行页的相对链接越出项目根时报错，历史页只警告。
- PW-09.6 `doctor` 不声称已经验证任意钩子，能报告 ProjectWiki 钩子是否安装。
- PW-09.7 相同输入生成相同的索引，检查命令不写文件。
- PW-09.8 配置顶层、`remind` 和 `remind.watch` 出现未知字段时报告 incomplete，退出码为 2。例如顶层写成 `dir_budget`、`remind` 里写成 `plan_stale_day`，或 watch 条目多写 `doc`。

### PW-11 提交时提醒同步文档

状态：已验证。

Agent 开发时频繁提交。提醒挂在 Git 提交上，对所有 Agent 宿主通用。

- PW-11.1 暂存的改动包含已登记的代码路径、但不包含对应文档时，`remind --staged` 输出 `docs-not-updated`，不拦截提交。
- PW-11.2 改动对应文档，或在提交信息里写带理由的 `Docs-Reviewed` 后，累计计数清零；没有理由的 trailer 不清零。
- PW-11.3 累计量达到 `block_at` 后，只有继续改代码且未复核的提交会失败。
- PW-11.4 不带 `--staged` 的汇总模式只提醒，不返回失败。
- PW-11.5 改动决策记录时列出仍链接它、但本次未改动的现行文档；项目配置了 `ask_user` 时，改动其中的需求、原则或决策文件才提醒先向用户确认。
- PW-11.6 安装仓库附带的 Git 钩子后，结构错误阻止提交，只改代码的提交输出提醒。
- PW-11.7 没有 Git 时报告 incomplete。配置里没有 `remind` 时，`remind` 和 commit-msg 钩子给出警告 `remind-not-configured`，退出码为 0，提交继续完成。
- PW-11.8 状态为执行中、长期没有提交的计划，以及已结束仍留在 `dev/` 的计划或审查，会被提醒。
- PW-11.9 `remind --staged` 的改动文件和行数来自启动时捕获的索引对象与 HEAD 树，不在运行期间重新读取实时索引；行数只用于提醒阈值，报告写明这一近似限制。
- PW-11.10 本仓库的提醒配置把规范正文变更与模板、demo 和入口摘要的核对关联起来；只改规范正文而没有同步这些位置时，`remind --staged` 给出 `docs-not-updated`。（人工验证）
  验收核对：PW-11.10，agent:codex，2026-10-30。
- PW-11.11 索引里有符号链接或子模块时，`remind --staged` 照常完成，这些路径计为改动但不计行数；两边对象 ID 相同的路径不读取内容。
- PW-11.12 暂存的 Markdown 文件相对 HEAD 新增了写着 `human:<名字>` 的行时，`remind --staged` 给出 `[user]` 提醒 `human-claim-added` 并列出名字；已有的行、代码块和行内代码里的示例、`human:<名字>` 这类占位写法不提醒。
- PW-11.13 待处理项（默认 `dev/inbox/*/*.md`）状态是待分诊且超过 `plan_stale_days` 天没有提交时提醒 `inbox-stale`；状态已完成却仍在 `dev/` 时提醒 `inbox-finished-not-archived`；没有可识别的状态行时提醒 `inbox-no-status`。收件箱的 `README.md` 不检查。

证据：[行为测试](../../tests/test_wiki.py)。

### PW-16 需求编号贯穿设计、计划与测试

状态：已验证。

- PW-16.1 现行文档或测试引用了不存在的需求编号或验收编号时报错。
- PW-16.2 需求编号重复、缺少状态行或状态值无法识别时报错。
- PW-16.3 已接受及之后状态的需求没有被任何设计或模块文档引用时警告。
- PW-16.4 已实现或已验证的需求，存在没有人工验证标记、也没有被任何测试引用的验收条目时警告；验收核对记录只能代替带人工验证标记的条目。工具只检查记录格式与引用，不把记录当作语义一致的证明。
- PW-16.5 已验证的需求没有带链接的证据行时警告。
- PW-16.6 执行中的计划没有"覆盖需求："一行时警告；已结束的计划和审查目录中的计划不检查。
- PW-16.7 配置 `requirements.id_pattern` 后，按项目自己的格式识别需求编号，例如 `REQ-AUTH-001` 或 `FR-1.2`；验收编号是需求编号加 `.` 和数字。只有与已定义编号前缀相同的文字才算引用，`UTF-8` 这类写法不会被当作编号。正则无效、能匹配空字符串，或 `requirements` 里有未知字段时，报告 incomplete。
- PW-16.8 没有人工验证标记的验收条目下写了验收核对记录时，`check` 给出 `trace-check-not-manual` 警告，这条记录也不消除 `trace-no-test`。

证据：[行为测试](../../tests/test_wiki.py)；[需求追踪决策](../decisions/requirement-traceability.md)。

### PW-17 知识页可以记录核对和复核期限

状态：已验证。

设计页、指南、调查结论这类知识会过期。只靠修改时间判断是否过期并不可靠：改过不代表核对过，没改也不代表还正确。

- PW-17.1 一级标题下、第一个二级标题之前可以写一行 `核对：<核对人>，<YYYY-MM-DD>`，多次核对用"；"分隔；同一区域可以写 `复核期限：<YYYY-MM-DD>`。只有以 `核对：` 或 `复核期限：` 开头的行才算，列表项和说明文字里提到这两个词时不解析。
- PW-17.2 核对行格式错误、日期无效、复核期限早于最近一次核对时，`check` 报错。
- PW-17.3 复核期限已到或已过、核对日期晚于今天时，`remind` 给出提醒；`check` 的结果不随日期变化。
- PW-17.4 配置要求某些路径必须写复核期限时，缺少复核期限的现行页给出警告。

证据：[行为测试](../../tests/test_wiki.py)。

### PW-19 可以导出为 OKF bundle

状态：已验证。

格式见 [OKF 规范](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)。导出不改变仓库里的写法。

- PW-19.1 `export-okf --out <目录>` 把现行知识文档复制到目标目录，保持相对路径，在每篇开头写入带 `type` 和 `title` 的 YAML frontmatter；过程目录和归档目录不导出。
- PW-19.2 状态映射为 OKF 的 `status`：当前有效对应 stable，草案对应 draft，被替代或废止对应 deprecated；项目通过 `status_values` 配置的同义状态按其映射处理；核对行映射为 `verified`，复核期限映射为 `stale_after`。
- PW-19.3 目标目录已存在且非空、或位于项目根目录内时，命令拒绝执行，不写任何文件。
- PW-19.4 已经带 frontmatter 的文档不重复添加，并在报告中列出。

证据：[行为测试](../../tests/test_wiki.py)。

### PW-20 归档可以由工具一次执行

状态：已验证。

接入项目多由 Agent 循环开发。手工移动文件、逐条改链接、补历史索引要多次读写，也容易漏改。

- PW-20.1 `archive <路径> --apply --expect <预览给出的 plan_sha256>` 把文档或目录移到预览给出的目的地，并按预览改写入链和出链；不带 `--apply` 时只预览，不写文件。计划哈希覆盖目的地、源内容和所有要改写的文件。
- PW-20.2 预览有错误、有无法机械改写的链接、计划哈希与 `--expect` 不一致、目的地已存在，或要改写的文件在读取后变化时，命令拒绝执行，不写任何文件。
- PW-20.3 改写只替换预览列出的链接目标，文件其余字节不变；报告列出每一处改写。
- PW-20.4 给出 `--summary <说明>` 时，在历史索引（`archive_index`，默认是归档根下的 `INDEX.md`）第一张表格的末尾追加一行；索引不存在或没有表格时拒绝执行，不写任何文件。
- PW-20.5 执行后对工作区重新运行 `check`，结果写进报告；检查有错误时返回 1。现行入口页的链接被改到归档里时给出警告。
- PW-20.6 执行前把所有改写内容写入临时文件；准备阶段失败时不移动源文件。提交阶段任一步失败时按相反顺序恢复已改写文件和移动操作，并在报告中说明回滚结果；进程被强制终止时可能留下临时文件或中间状态。
- PW-20.7 目录归档的计划哈希覆盖目录里实际移动的每一项，包括非 Markdown 文件、被 `exclude` 排除或未跟踪的文件和空目录；预览后有任何增加、删除或修改，执行拒绝，不写任何文件。预览列出全部随目录移动的非 Markdown 文件。

证据：[行为测试](../../tests/test_wiki.py)。

### PW-21 验证记录由工具生成

状态：已验证。

计划里的验证记录手写时，命令、数量和哈希可能与实际运行结果不一致。

- PW-21.1 `verify` 依次运行配置里登记的命令，记录每条命令的运行目录、退出码、用时和输出摘要（默认最后几行，可以改为前几行），输出可以直接放进计划"验证"一节的 Markdown。
- PW-21.2 记录写明运行日期、Git HEAD、未提交改动的文件数、配置文件的 sha256 前缀，以及配置里登记的文件的 sha256 前缀。
- PW-21.3 任何一条命令失败或超时，`verify` 返回 1，并在记录里写明是哪条命令；只运行其中几条时，记录列出没有运行的命令。
- PW-21.4 命令按参数数组执行，不经过 shell；配置无效或运行目录越出项目根时，报告 incomplete，不运行任何命令。

证据：[行为测试](../../tests/test_wiki.py)。

### PW-22 生成目录可以由工具写入

状态：已验证。

- PW-22.1 `index --write` 把目录写到 `generated_index`；内容没有变化时不改文件，报告写明是否改动。

证据：[行为测试](../../tests/test_wiki.py)。

### PW-23 文档里的清单与代码对账

状态：已验证。

规则名、配置项、命令参数这类能列成集合的内容，代码改了而文档没改时，读者看到的说明就过时了。

- PW-23.1 配置 `reconcile` 后，`check` 用登记的正则表达式分别从文档和代码里取出名称；代码里有、文档里没有，或者文档里有、代码里没有，都报错，错误里写出名称。
- PW-23.2 `ignore` 里列出的名称不参与比较。文档或代码一侧没有匹配到任何文件或名称时报错，避免正则写错后检查静默通过。
- PW-23.3 本仓库的检查配置登记工具说明与 `wiki.py` 之间的规则名对账，检查通过。

证据：[行为测试](../../tests/test_wiki.py)。

### PW-24 找出没有入口的文档和资产

状态：已验证。

Agent 不断新建文件。没有任何文档链接到的页面，读者按导航找不到；没人引用的截图和原型会越积越多。

- PW-24.1 现行知识文档（不含入口页、模块入口和过程目录里的文档）没有被任何现行文档链接时，`check` 给出 `orphan-page` 警告。只被归档文档链接不算有入口。
- PW-24.2 知识目录和模块文档目录里的非 Markdown 文件没有被任何现行文档链接时，`check` 给出 `orphan-asset` 警告；链接到所在目录也算引用。配置文件、生成目录、基线文件和以 `.` 开头的文件不算资产。
- PW-24.3 配置 `orphan_ignore` 里匹配的路径不报告。

证据：[行为测试](../../tests/test_wiki.py)。

### PW-25 计划写明负责人

状态：已验证。

多个 Agent 同时工作时，需要知道每项执行中的工作由谁负责，避免两个执行者改同一批文件。

- PW-25.1 计划的状态行可以写 `负责：human:<名字>` 或 `负责：agent:<名字>`（英文写 `Owner:`）；写了但不是这两种前缀时，`check` 报错。
- PW-25.2 `remind` 列出状态为执行中或阻塞的计划，以及各自的负责人；没写负责人的标为未写。

证据：[行为测试](../../tests/test_wiki.py)。

### PW-26 新建文档的名称可预测且移动安全

状态：已验证。

文档名主要用于导航和检索，不承担全局编号、状态机或版本管理。

- PW-26.1 文档所在目录中出现只差大小写的同名 Markdown 文件时，`check` 报错；大小写不同的路径在大小写不敏感的文件系统上视为冲突。
- PW-26.2 `check-new` 和暂存检查发现新文档路径含空格、`#`、`%` 或括号时，报错并说明归档链接不能安全改写。
- PW-26.3 新建检查遇到 `plan.md`、`decision.md`、`inbox-item.md` 这类模板占位名，或文件名含状态、版本词时，只给警告；已有文件不因这些建议产生存量警告。
- PW-26.4 命名检查不要求 ASCII、小写、短横线、统一日期前缀或全局编号：中文名、大写字母、下划线、日期前缀和不带编号的文件名都不产生命名警告。
- PW-26.5 暂存检查不对归档根下的新增路径，以及内容不变、文件名不变的移动做命名检查；改成新文件名的重命名和新文件照常检查。

证据：[行为测试](../../tests/test_wiki.py)。

## 质量要求

文档使用具体、清楚的技术语言。编写者需要删除无信息量的铺垫、翻译腔和未定义的内部行话。机械检查只辅助发现问题，文风结论仍需阅读全文。

工具保持本地可运行。`check`、`remind`、`doctor`、`check-new` 和归档预览只读。写文件的只有 `archive --apply`、`index --write` 和 `export-okf`，都先核对目标状态，不静默覆盖内容；`verify` 只运行配置里登记的命令。不得把不完整的检查报告为通过。

核对行、复核期限续期、人工签收、需求状态和稳定知识的正文由人或 Agent 写，工具不自动生成。
