# Design trade-offs of documentation automation

> English translation of [文档自动化的设计取舍](../../design/automation.md). The Chinese page is authoritative: if the two differ, the Chinese page applies.

Requirements: PW-03, PW-06, PW-07, PW-09, PW-11, PW-12, PW-13, PW-14, PW-15, PW-16, PW-17, PW-18, PW-19, PW-20, PW-21, PW-22, PW-23, PW-24, PW-25, PW-41, PW-42, PW-44, PW-45, PW-46, PW-48.

The commands of the checker are in the [tool entry](../../../scripts/wiki/en/README.md), the configuration fields and every rule are in [Configuration and rules](../../../scripts/wiki/en/reference.md), the fixed forms the tool reads are in [Forms the tool reads](../../../scripts/wiki/en/formats.md), and the development workflow rules that the tool cannot enforce are in [Development workflow rules](../../../scripts/wiki/en/workflow.md). These four are kept in `scripts/wiki/`, so an adopting project gets them when it copies the tool and need not go back to the ProjectWiki repository to look up formats or workflow; they link to one another and link only to files inside `scripts/wiki/`. This page explains why the tool is designed this way and what it deliberately does not do.

## `check` is a deterministic gate

`check` is read-only and gives the same result for the same input, so it can be put in `pre-commit` to block commits and in `pre-merge-commit` to block merges without conflicts. To this end:

- Judgments that depend on the date (a review-by date that has passed, a plan that has not been updated for a long time) are in `remind`, not in `check`.
- It does not go online, and external links are not verified.
- Relative links are resolved from the file that contains the reference, with exact case checked and no fallback to the repository root. A fallback would hide links that cannot be opened in other tools.
- Problems in historical documents are lowered to warnings. History records the situation at the time, and the old source code and old contracts may no longer exist.

The tool parses only a few lines of fixed format: the status line, the verification line, requirement IDs, and the verdict line of a review finding. The rest of the text is treated as ordinary Markdown, and frontmatter is not required; the reasons are in the [status line decision](../../decisions/status-line.md) (in Chinese). These fixed formats are written in the text, and to a person they also read as an ordinary sentence.

Each keyword and value has only one Chinese form and one English form, all listed in [Forms the tool reads](../../../scripts/wiki/en/formats.md). The parsing regular expressions of `wiki.py` are generated from the same keyword table, and the tool's tests check this table against formats.md item by item, so the tests fail whenever the code recognizes one word more or the document lists one word more. The more synonyms there are, the harder it is for readers to judge which form is valid; when a project wants to use its own status words, it maps them in the configuration, and the defaults are not widened.

## The staged check reads only the Git index

Agents and people alike often fix a file in the working tree and do not stage it. `check --staged` reads the configuration, the text, and the link targets from the Git index, so what it checks is exactly the content about to be committed, and a fix in the working tree cannot hide an error in the staging area. When a required input cannot be read, the index has conflicts, or there is no Git, it reports incomplete and does not fall back to the working tree to go on checking, because that would report an unfinished check as passed.

For a project that has registered neighboring repositories (`repos`), the staged check also reads the HEAD commit these repositories had when the check started, in order to verify cross-repository links, and the report gives the commit IDs. The result can still be reproduced: the same index plus the same commits of the neighboring repositories gives the same conclusion. The working trees of neighboring repositories are not read, otherwise the same index would give different conclusions at different times; changes not yet committed in a neighboring repository neither make the check fail nor hide problems. The trade-offs are in the [decision on cross-repository links](../../decisions/cross-repo-links.md) (in Chinese).

When a document itself cannot be read (it is a symbolic link, or it is not UTF-8), `check` reports one error for that document and goes on checking the others. Earlier it reported incomplete at the first such document, so a repository with a dozen or so symlinked documents got no other conclusion and could not see which files had to be dealt with. This does not report an unfinished check as passed: each unreadable document has its own error, and the result is a failure. Requirement files and review directories have to be checked as a whole, since the IDs refer to one another and nothing can be judged with one file missing, so these two places still report incomplete.

The check does not enter symlinked directories. The index holds only the link itself, so the staged check cannot read the content behind it; if the working-tree check followed it, the same content would get different conclusions in the two checks. Links that point behind a symbolic link are reported as broken links, with the reason stated in the message; when the content is maintained elsewhere, the project writes the symbolic link into `exclude`, and these links are then counted instead, with the report giving the number not checked. They are excluded explicitly by the project rather than let through by the tool by default, because the tool cannot tell whether a symbolic link deliberately points elsewhere or is a bad link left over from a move.

## Reminders hang on Git commits

A document usually goes unchanged not because the rule was not written down but because the person or agent changing the code did not think of it at the right moment. Agents commit very frequently during development, and every agent host and Git client runs Git hooks, so the reminders hang on commits and do not depend on the plugin mechanism of any one host.

The counts are computed only from the Git history, the staging area, and the commit message, and no separate state file is kept. Staged mode captures the objects of the index and of HEAD when the command starts; the file list and the line counts are both computed from this snapshot, and the live index is not read again during the run; only the files whose object IDs have changed are read, so the time taken grows with the size of the change and not with the size of the repository. Line counts are used only for threshold reminders and may differ slightly from Git's `numstat` for binary files or unusual line endings. Switching branches, working copies, or machines gives the same result.

By default the reminders do not block commits. A single code change gets only an informational notice, a review is required only when the accumulated amount reaches the threshold, and only on reaching `block_at` is a commit blocked that goes on changing code without a review. Requiring every commit to update the text or to write `Docs-Reviewed`, even if the hook returned success, would get agents into the habit of filling in a reason offhand, and the reminders would lose their effect. Accumulated review allows omissions to exist temporarily within the threshold, at the cost that an omission may be found only later; when the text is already known to be wrong, it still has to be updated at once. When the configuration has no `remind` yet, commit-msg gives the warning `remind-not-configured` with exit code 0. An adoption can install the hooks first and write the reminder configuration afterwards: reminders can be computed only when there is a configuration. The exact strength and the handling are under [Documentation reminders at commit time](../../../scripts/wiki/en/reference.md#documentation-reminders-at-commit-time).

A watch group itself can also become inaccurate, and the tool gives notice in two cases. When a pattern matches no file, the group is watching less content with no signal at all, and `check` gives the warning `watch-path-dead`. Code patterns are often listed in groups by file type, and one type having no files for the time being is not drift; reporting each one would only turn the warnings into noise, so code patterns that contain wildcards are reported only when the whole group matches nothing; the cost is that it goes unnoticed when the directory that an individual wildcard pattern in the group points to is moved away. When a document has been written but not committed, the history has no starting point, and counting every change within the scan range as debt would not give a useful number, so `remind` records this group as 0 and prompts you to commit the document first (`docs-uncommitted`). Staged mode reads only the index and cannot see unstaged documents, so its behavior is unchanged.

ProjectWiki's own configuration additionally registers the `system-rules` watch group: when the text of the specification is changed, it reminds you to check `templates/`, `demo/`, and the entry summaries. An adopting project replaces the `code` and `docs` of this group with the matching paths of its own stable knowledge, templates, and examples, by its own directories.

## Only a few commands write files

Steps whose result can be computed exactly from existing input are carried out by the tool, for example moving files into the archive, rewriting links, and writing the generated index and the verification record. Records that need judgment, such as verification lines, renewals of review-by dates, manual sign-offs, and requirement statuses, are written by people or agents. The trade-offs are in the [decision on automating mechanical steps](../../decisions/automation-writes.md) (in Chinese).

Every command that writes files first checks the state of the target: archiving uses the plan hash to confirm that nothing has changed since the preview, and does not write when the destination already exists; archiving first prepares temporary files with the rewrites, and when committing them fails it tries to roll back in reverse order; the generated index leaves the file alone when the content has not changed; export writes only to an empty directory outside the project. The Git hooks only check and remind and never modify files or the staging area, otherwise the committed content would differ from what the author saw.

`verify` runs the commands registered in the configuration of the repository. Commands are written as argument arrays and do not go through a shell: a pipe swallows the exit code of the preceding command, which is exactly the common mistake in handwritten verification records.

## What is deliberately not done

- It does not judge whether the text is well written, nor whether the content of the documents matches the code. Writing quality is reviewed by people against the [writing standard](../standards/writing.md), and whether content is out of date is left to verification lines, reminders, and reviews.
- It does not understand code structure. List reconciliation compares only the text extracted by regular expressions, and false positives are excluded with `ignore`.
- It is not a Markdown renderer and does not promise to support every dialect or the import syntax of every host.
- It does not judge whether a status line is true. A status line states only the status the author declares.
- It cannot prevent `git commit --no-verify`, nor can it inspect other hook managers and build tasks; `doctor` reports these as unknown. A check that an adopting project has not really enabled must not be written up in the documents as enabled.
