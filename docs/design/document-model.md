# 文档模型

对应需求：PW-01、PW-02、PW-04、PW-05、PW-12、PW-14、PW-15、PW-16、PW-17、PW-18、PW-25、PW-26。

## 接入项目的目录

| 路径 | 职责 |
|---|---|
| `AGENTS.md` | 给 Agent 的全局硬规则和按任务阅读的路由 |
| `docs/` | 当前有效的需求、原则、设计、规范和决策记录，原位维护 |
| `dev/` | 开发过程：路线图、计划、审查、待处理项 |
| `archive/` | 已结束的过程材料和整篇失效的文档，保持原相对路径 |
| `<模块>/README.md` | 模块入口：职责、相关契约、验证方式 |
| `<模块>/docs/` | 只属于这个模块的设计和决策，内容多了再建 |

三个根目录并列，`archive/` 可以在第一次归档时再建。小模块只写 README，不必建模块 `docs/`；全局文档里的模块表直接链接模块入口，不在 `docs/` 下另建一套模块镜像目录。模板见 [`templates/project/`](../../templates/README.md)，完整例子见 [NoteBox](../../demo/README.md)。

## 页面职责

| 页面 | 内容 | 更新方式 |
|---|---|---|
| 入口 | 适用规则、阅读条件与目标链接 | 路由变化时更新 |
| 当前知识 | 需求、原则、结构、契约与规范 | 持续原位维护 |
| 决策记录 | 重要选择的背景、替代方案、结论和后果 | 保留原决定；改变决定时说明替代依据 |
| 计划 | 某项工作的步骤、进度、验证与交接 | 随这项工作更新 |
| 路线图 | 方向、顺序和里程碑入口 | 方向或依赖变化时更新 |
| 待处理项 | 观察、请求、推测、核实依据和去向 | 分诊与处理时更新；处理完写明去向后归档 |
| 审查 | 一次审查的范围、分路、每条问题及其核对、方案和签收 | 审查进行中持续追加，结束后整个目录归档 |
| 归档 | 已结束的过程或整篇退役内容 | 保留来源，避免覆盖历史 |

文档不必统一采用复杂的 frontmatter。`docs/wiki.json` 登记范围、入口、角色和预算；正文使用人能理解的标题、范围、状态及来源。计划、决策记录和待处理项在标题下第一行写状态，例如 `状态：执行中。`，工具据此提醒长期未更新或已结束未归档的计划和待处理项，并阻止入口页链接到被替代的文档。写法和取值见[工具读取的写法](../../scripts/wiki/formats.md#计划决策记录和待处理项的状态行)，为什么用正文首行见[状态行决策](../decisions/status-line.md)。多人或多个 Agent 同时工作时，计划的状态行里再写负责人，例如 `负责：agent:kiro。`，写法与核对人相同；`remind` 据此列出谁在负责哪项执行中的工作。同一项工作的进度不在 frontmatter、路线图勾选或另一份总览里再写一套；这些位置如果还在，必须与这一行相同。

## 当前知识与目标设计

确认需求表示项目接受这个目标，不表示实现已经完成。设计页应写清它描述当前行为还是未来方案；当前实现的限制和对应工作链接应可查到。

工具检查配置名称、链接或字段时，只证明所检查的部分。设计生效状态与机器检查结果分别表达，不能用一个通过标记替代整篇文档的复核。

## 决策与当前设计

架构决策记录（Architecture Decision Record，ADR）解释一项选择为什么成立。当前需求、原则和设计表达今天适用的内容，并在需要时引用 ADR。

只影响某个模块的 ADR 放在模块的 `docs/decisions/`；跨模块 ADR 放在根 `docs/decisions/`。第一版按需创建这些目录，使用描述性文件名，避免协作者申请同一个全局顺序号。

已采用的 ADR 不因实施完成而归档。整项决定被替代或其适用对象退役后，可以按[生命周期规则](lifecycle.md)归档，并保留替代关系。

ADR 和当前设计必须一致。决定改变时，在同一次改动中更新仍描述旧结论的现行文档；设计改变推翻了已采用的决定时，补新的 ADR。具体步骤见[开发流程](../guides/workflow.md#决定或设计变化时同步文档)。

## 身份与路径

普通 Markdown 链接继续使用可直接打开的路径。配置中的可选 ID 用于检查当前身份和替代关系，不要求专用链接语法。

当前有效正文在同一适用范围内不得出现重复身份。历史版本可以保留同一个逻辑 ID，由归档路径和来源版本区分；恢复历史文档不要求删除旧证据。

摘要描述内容。阅读条件放在导航旁，因此同一设计页可以分别从功能开发入口和故障维护入口进入。

## 文件命名

文件名是导航提示，不是完整身份。稳定知识使用能概括主题的描述性名称；不把 `draft`、`final`、`latest`、`done` 或版本号当作唯一身份，状态写在正文状态行。需求编号、审查问题编号等需要稳定引用的 ID 写在正文中，并且不复用。

固定入口使用 `README.md`、`AGENTS.md`、`CLAUDE.md`、`INDEX.md` 和 `CHANGELOG.md` 等约定名称。复制 `templates/plan.md`、`templates/decision.md` 等占位模板后，应把文件改成具体主题名。

新文档路径不得含空格、`#`、`%` 或括号；这些字符会使归档链接需要转义，而工具无法保证改写后仍指向同一目标。目录内只差大小写的 Markdown 文件也视为冲突。其他风格（是否使用中文、ASCII、小写短横线、长度限制或日期前缀）由接入项目自行决定，工具只在新建检查中提示状态词、版本词和模板占位名。归档和只换目录、不改文件名的移动保留原名，不算新建，所以已有的旧文件名不妨碍归档和搬迁。

新建前运行 `python3 scripts/wiki/wiki.py check-new <路径> --root .`。它按完整原相对路径检查当前文件和 `archive/<原相对路径>`，历史命中是提示，不永久占用名称；归档保持原文件名，不自动加序号。

## 变更日志

`CHANGELOG.md` 按版本记录用户能感知的行为变化和升级注意事项。它属于稳定知识：发布后的段落不再改写，只追加新版本。开发步骤、内部重构和验证流水不写进变更日志，它们属于计划和提交记录。

有发布流程的项目可以在发布时检查变更日志里是否已有当前版本的段落，没有就停止发布。这类检查由项目自己的发布脚本完成，ProjectWiki 工具不检查它。

## 需求条目与追踪

需求文件里每条需求是一个以编号开头的标题，标题下一行写状态，验收条件逐条列出、各带子编号，写成可以检查的形式。具体写法、状态取值和编号怎样分配见[工具读取的写法](../../scripts/wiki/formats.md#需求条目)；项目已有别的编号格式时保留原编号，在配置里登记格式，见[配置与规则](../../scripts/wiki/reference.md#需求追踪)。

验收条件默认由测试证明。只有命令确实证明不了的条目才标"（人工验证）"，并由核对的人或 Agent 写一行验收核对记录。这行记录只对标了人工验证的条目有效：如果任何条目都能用一行核对记录代替测试，能写测试的条目也会被一句"已核对"放过。已验证的需求要有一行"证据："，链接到测试或验证记录。

下游只引用编号，不复制需求正文：设计文档写"对应需求：PW-11"，计划写"覆盖需求：PW-11"，测试在说明文字里写验收编号。编号把需求、设计、计划和测试串起来，检查工具据此发现孤立的需求、没有测试的验收条件和引用错误的编号。格式和理由见[需求追踪决策](../decisions/requirement-traceability.md)。

确认但还没实现的需求状态是"已接受"，仍然属于稳定知识。实现之后改为"已实现"，有证据后改为"已验证"。需求被取消时改为"已废止"，不删除编号，避免同一个编号以后指向别的内容。

## 核对记录与复核期限

知识页可以在一级标题下、第一个二级标题之前写一行核对记录，会过期的页面再写复核期限，例如 `核对：agent:kiro，2026-10-28；human:clarence，2026-11-02。复核期限：2027-04-28。`。写法见[工具读取的写法](../../scripts/wiki/formats.md#核对行与复核期限)。

核对人统一写成 `human:<名字>` 或 `agent:<名字>`，审查核对表的核对人、问题作者、负责人和签收人也用这一写法。由此可以分出三个信任级别：没有核对行是未核对；只有 Agent 核对过；有人工核对。Agent 不得把自己写成 `human:`。工具分不出一行是谁写的，所以配置了 `remind` 的项目里，提交新增 `human:` 名字时会出现 `[user]` 提醒，请提交者向用户确认；其余靠评审和提交记录核对。

复核期限是绝对日期，只给确实会过期的页面设置，例如运维手册、外部事实、调查结论；核对时一并续期。到期后由 `remind` 提醒。配置可以要求某些路径必须写复核期限，或者必须有人工核对。这套写法借鉴自 Open Knowledge Format 的 `verified` 和 `stale_after`，取舍见[核对记录与 OKF 决策](../decisions/verification-line-and-okf.md)。

## 审查记录

一次审查放在一个目录里：`dev/reviews/<开始日期>-<主题>/`。目录里有一个 `README.md`，写范围、基准提交、分路方式、核对分组和汇总签收；每一路一个分路文件，例如 `r01-input-boundary.md`。只有一路时，问题可以直接写在 `README.md` 里。模板见 [`templates/review/`](../../templates/review/README.md)，示例见 [demo 的标题输入审查](../../demo/dev/reviews/2026-10-28-title-input/README.md)。

目录名以开始日期开头，是文件名不写日期的一个例外：同一主题会多次审查，每次一个新目录，按日期才能找到最近一次。这个日期只记录审查从哪天开始，之后不再改，不表示进度。

分路的方式由审查者决定：可以按模块、主题、一个具体问题、一组文件或一类缺陷来分，路数不固定。路号由负责汇总的人分配，中途追加的路也先在 README 登记再开始写，这样并行工作的执行者不会取到同一个路号。

每条问题是分路文件里的一个二级标题，标题以问题编号开头，例如 `## r01-1 只含零宽空格的标题会通过校验`。编号在整次审查里唯一，从发现、核对、方案、签收一直用到实施。问题小节依次包含判定行、观察、推测、核对表、方案和签收，写法和判定取值见[工具读取的写法](../../scripts/wiki/formats.md#审查问题)。几条要点：

- 观察是作者写下的事实，包括文件与行号、命令与输出。核对开始后不再修改这一段。
- 第二轮复查、换人或换模型复查都在核对表里追加一行。核对人不能是作者。
- 方案只为成立或收窄的问题写。一个修复覆盖多条问题、需要单独排期时，改成同目录下的 `plan-<主题>.md`。

核对的是问题本身，所以核对结果直接写进问题小节，不另建核对文件；轮次、模型和日期写在表格里，不写进文件名。这样一次审查的文件数大约等于路数加一，不会随轮次和参与者成倍增加。

## 证据与待处理项

验证记录说明被验证的代码或配置、执行命令、结果和已知限制。命令、结果和被测文件的哈希用 `verify` 的输出，不手写；人工核对的内容写在后面。之后写入的记录不属于被测代码快照。

待处理项应将观察与推测分开。接受调查不等于证实问题，分流到计划不等于修复完成。可以复用已有的 issue 系统；采用仓库内收件箱时，按类型放在 `dev/inbox/` 下，一条一文件，避免把所有人发现的内容追加到同一大文件。

一条一文件会让收件箱不断变长，所以每条都要有结束方式：分诊后转成计划、写回当前知识、判为重复或决定不处理，把去向写进条目，状态改为"已完成"，然后归档。归档而不是删除，是因为"不处理"的理由以后还会被问到：同名条目再次新建时，`check-new` 会提示归档里的那一条。配置了 `remind` 的项目会收到长期待分诊和已完成未归档的提醒；项目模板默认给收件箱设了目录文件数预算，不依赖 `remind`。
