# 文档自动化的设计取舍

对应需求：PW-03、PW-06、PW-07、PW-09、PW-11、PW-12、PW-13、PW-14、PW-15、PW-16、PW-17、PW-18、PW-19、PW-20、PW-21、PW-22、PW-23、PW-24、PW-25。

检查工具的命令写在[工具入口](../../scripts/wiki/README.md)，配置字段和每条规则写在[配置与规则](../../scripts/wiki/reference.md)，工具读取的固定写法写在[工具读取的写法](../../scripts/wiki/formats.md)。这三份放在 `scripts/wiki/` 里，接入项目复制工具时一起拿到，不需要回到 ProjectWiki 仓库查格式。本页说明工具为什么这样设计，以及它有意不做哪些事。

## `check` 是确定的门禁

`check` 只读，相同输入给出相同结果，所以可以放进 `pre-commit` 拦截提交。为此：

- 和日期有关的判断（复核期限到期、计划长期没更新）放在 `remind`，不放在 `check`。
- 不联网，外部链接不验证。
- 相对链接按引用所在文件解析，检查精确大小写，不回退到仓库根目录。回退会掩盖在别的工具里打不开的链接。
- 历史文档里的问题降为警告。历史记录的是当时的情况，旧源码和旧契约可能已经不在了。

工具只解析几行固定格式：状态行、核对行、需求编号、审查问题的判定行。其余正文按普通 Markdown 处理，不要求 frontmatter，理由见[状态行决策](../decisions/status-line.md)。这些固定格式写在正文里，人读起来也是一句普通的话。

每个关键词和取值只有一个中文写法和一个英文写法，全部列在[工具读取的写法](../../scripts/wiki/formats.md)里。`wiki.py` 的解析正则从同一张关键词表生成，工具测试逐项核对这张表和 formats.md，所以代码多认一个词或文档多写一个词，测试都会失败。同义词越多，读者越难判断哪种写法有效，项目要用自己的状态词时在配置里映射，不扩大默认值。

## 暂存检查只读 Git 索引

Agent 和人都常在工作区里修好了文件、却没暂存。`check --staged` 从 Git 索引读取配置、正文和链接目标，检查的就是即将提交的内容，工作区里的修复掩盖不了暂存区里的错误。读不到必需的输入、索引有冲突或没有 Git 时，报告 incomplete，不退回工作区继续检查，因为那样会把一次没完成的检查报告成通过。

## 提醒挂在 Git 提交上

文档漏改通常不是因为规则没写，而是改代码的人或 Agent 没有在合适的时候想起来。Agent 开发时提交很频繁，所有 Agent 宿主和 Git 客户端都会运行 Git 钩子，所以提醒挂在提交上，不依赖某一个宿主的插件机制。

计数只从 Git 历史、暂存区和提交信息计算，不另存状态文件。暂存模式在命令启动时捕获索引与 HEAD 的对象，文件列表和行数都从这份快照计算，不在运行中重新读取实时索引；只读取对象 ID 变化的文件，所以耗时随改动大小增长，不随仓库大小增长。行数只用于阈值提醒，二进制文件或特殊换行可能与 Git 的 `numstat` 略有差异。换分支、换工作区副本或换机器，看到的结果都一样。

提醒默认不拦截提交。每次都被拦下，Agent 很快会养成随手写 `Docs-Reviewed` 的习惯，提醒就失去了作用。`block_at` 只给累计欠账设上限。提醒分两类：`[agent]` 由 Agent 自己处理；配置了 `ask_user` 的路径发生变化时，`[user]` 提醒提交者先问用户。

ProjectWiki 自己的配置另外登记 `system-rules` 观察组：修改规范正文时，提醒核对 `templates/`、`demo/` 和入口摘要。接入项目按自己的目录把这组 `code` 和 `docs` 替换成对应的稳定知识、模板和示例路径。

## 只有少数命令写文件

能从现有输入精确算出结果的步骤由工具执行，例如移动归档、改链接、写生成目录和验证记录。需要判断的记录，例如核对行、复核期限续期、人工签收和需求状态，由人或 Agent 写。取舍见[机械步骤自动化决策](../decisions/automation-writes.md)。

写文件的命令都先核对目标状态：归档用计划哈希确认预览之后没有变化，目的地已存在时不写；归档先准备改写临时文件，提交失败尝试逆序回滚；生成目录内容没变时不动文件；导出只写项目以外的空目录。Git 钩子只检查和提醒，从不修改文件或暂存区，否则提交的内容会和作者看到的不一致。

`verify` 运行仓库配置里登记的命令。命令写成参数数组，不经过 shell：管道会吞掉前一条命令的退出码，而这正是手写验证记录时常见的错误。

## 有意不做的事

- 不判断正文写得好不好，也不判断文档内容和代码是否一致。写作质量按[写作规范](../standards/writing.md)人工复核，内容是否过时靠核对行、提醒和审查。
- 不理解代码结构。名单对账只比较正则取出的文字，误报用 `ignore` 排除。
- 不是 Markdown 渲染器，不承诺支持所有方言和宿主的导入语法。
- 不判断状态行是否属实。状态行只说明作者声明的状态。
- 阻止不了 `git commit --no-verify`，也检查不了其他钩子管理器和构建任务；`doctor` 对这些报告为未知。接入项目没有真的启用的检查，不能在文档里写成已启用。
