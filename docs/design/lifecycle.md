# 文档维护与归档

对应需求：PW-05、PW-06、PW-07、PW-08、PW-20、PW-24。

## 先判断文档是否仍有当前职责

`archive/` 主要保存已结束的开发过程材料。稳定知识中的局部过时内容直接修订，修订历史由 Git 保留。

| 内容 | 通常处理方式 |
|---|---|
| `module-structure.md`、现行接口、需求与原则 | 原位维护；不因一次修改或任务完成归档 |
| 仍有效的 ADR | 保留在所属知识范围内 |
| 已完成或取消的计划 | 核对剩余事项与知识更新后归档 |
| 处理完的待处理项 | 在条目里写明去向（计划、当前知识、重复的条目或不处理的理由），状态改为已完成后归档 |
| 实验报告与验证原始记录 | 工作结束后可归档；可复用结论整理进当前知识 |
| 仍在使用的状态页 | 归并当前状态；只处理已经结束的完整历史记录 |
| 已删除模块的专属文档 | 确认没有其他适用对象后整篇归档 |
| 被替代的决定或整篇废弃方案 | 记录原因、适用范围和替代目标后归档 |

正在等待、阻塞或仍约束当前行为的内容，不因时间久或超出篇幅预算而自动归档。

没有任何现行文档链接到的知识页和资产，读者按导航找不到，`check` 会给出警告（`orphan-page`、`orphan-asset`）。处理方式三选一：从对应的导航或入口链接它；把内容并进另一页；或者确认它已经没有当前职责，按本页规则归档或删除。截图、原型这类资产没人引用时通常直接删除，旧版本由 Git 保存。

一次审查的目录要整体归档：README 状态改为"已完成"、所有方案都已实施或转出之后，把 `dev/reviews/<日期>-<主题>/` 整个移到 `archive/dev/reviews/<日期>-<主题>/`。只要还有一条方案没有结束，就把整个目录留在原地，不拆开归档。目录内部的相对链接随目录一起移动，仍然有效。

## 已在实际项目中出现过的失效方式

下面几种情况都在接入调查中实际出现过。处理文档时遇到相同迹象，按右列处理。

| 现象 | 后果 | 处理方式 |
|---|---|---|
| 计划全部完成或已经取消，仍留在 `dev/` 并标着"执行中" | 进行中的工作列表失真，读者无法判断哪些还在做。一个项目曾有两千多个这样的文件 | 计划结束时按本页规则归档。`remind` 只认状态行：状态已是完成却仍留在 `dev/` 时会提醒；状态仍写着执行中时，它发现不了 |
| 同一项工作的进度同时写在状态页、路线图勾选和计划总览 | 三处会给出不同结论。曾出现状态页写没有进行中的任务，计划总览把另一项标为当前焦点，路线图文件仍标进行中 | 进度只写在该计划的状态行。路线图只链接计划。状态页只在两份以上计划同时进行时汇总，不重写步骤 |
| 状态行与步骤清单不一致：状态已是完成仍有未勾选步骤，或步骤已全部勾完状态仍是执行中 | 「已完成」和剩余工作互相否定，读者无法判断能否归档 | 归档前改到一致。每个未勾选步骤写明去向：另开计划、写回当前知识，或明确取消。工具只识别状态行，发现不了这种不一致 |
| 整个目录移动后，相对链接多写或少写一层 `../` | 链接在编辑器里看不出问题，实际已经失效 | 不手工移动。用 `archive` 预览，再用 `archive --apply` 执行，工具改写受影响的链接并在执行后运行 `check` |
| 同一功能在两个位置各有一套说明，内容逐渐不同 | 读者不知道该信哪份 | 只保留一份当前正文，另一处改成链接，或者整篇归档 |
| 功能已经落地，知识层仍保留「现状 / 实现 / 路线」连载，或把审查报告放在架构目录 | 同一功能有多套说明，方案过程被当成当前行为 | 保留一篇描述当前行为的文档。连载里的过程章节和审查报告结束后归档；仍然有效的约束写回这篇设计 |
| 故障根因和修复过程放在系统设计目录里 | 修复流水被当成现行设计 | 根因与过程放 `dev/`，结束后归档；仍然有效的约束写回设计页 |
| 规范要求检查链接或格式，但没有工具执行 | 规范写着"链接已验证"，实际已经失效 | 写进规范的约束要有对应检查，否则只能写成建议 |
| 审查的每一路、每一轮、每个模型、每次签收各建一个文件，平铺在同一目录 | 一次审查几十个文件，同一条问题的核对结果分散在多处 | 一次审查一个日期目录，核对写进问题小节，轮次和模型写在表格里 |

## 新建时检查历史

新建 `dev/plans/example.md` 前，检查当前位置及 `archive/dev/plans/example.md`。工具提供只读入口：

```bash
python3 scripts/wiki/wiki.py check-new dev/plans/example.md --root .
```

匹配的是完整原相对路径，不能只按 `README.md` 等 basename 判断。发现同源历史后，阅读其范围和结论，再判断是恢复、重复创建，还是新主题复用路径。

历史同名本身是提示。覆盖已有正文、重复当前身份、覆盖归档目标或使已知旧引用悄悄改变含义，才需要停止并解决。新建检查不能代替归档写入前的最终冲突核对。

## 整页归档

默认保持文件名和相对目录：

```text
dev/plans/example.md → archive/dev/plans/example.md
core/docs/retired-design.md → archive/core/docs/retired-design.md
```

不把模块文档重新归类到另一套镜像目录。目标已存在时明确报告冲突，不覆盖、不自动编号，也不把未完成的迁移报告为成功。

归档分两步，先预览再执行：

```bash
python3 scripts/wiki/wiki.py archive dev/plans/example.md --root .
python3 scripts/wiki/wiki.py archive dev/plans/example.md --root . --apply --expect <预览给出的 plan_sha256> --summary "一行说明"
```

执行时移动文件，改写预览列出的入链和出链，在历史索引的表格里加一行，然后运行 `check`。预览之后任何输入变化都会让计划哈希对不上，执行就会拒绝。文件只移动，不暂存。

从活文件中提取的完整历史记录没有独立原路径。若以后需要保存这种片段，应放到 `archive/<原父目录>/<源文件名>.history/<记录标识>.md`，同时记录来源和提取边界；`.history` 后缀避免它与整页归档的目标 `archive/<原父目录>/<源文件名>` 冲突。工具只处理整页或整个目录，不自动裁切或追加历史片段。

## 控制链接迁移成本

保持现行知识页路径稳定，可以避免大多数迁移。真正移动整页时，`archive --apply` 改写登记文档里指向它的链接，让它们继续指向同一篇内容；登记文档以外的引用（代码注释、排除目录）需要另行搜索。

- 所属导航直接链接当前正文或适当的历史入口。入口页的链接被改进归档时，工具会警告，由人决定改为链接当前正文，还是保留历史链接。
- 普通相对出链按移动前位置解析，再根据目标是否移动重新计算路径。
- 历史证据保留当时版本，不能统一改成最新文档。
- 有外部书签或较多入链时，可在旧路径保留简短跳转说明；普通 Markdown 需要读者再打开其中链接。
- `old.md#section` 不会通过短跳转页自动定位新正文。带锚点的已知入链需单独核对。
- 跳转页占位期间，旧路径不能静默复用给无关正文。复用前核对引用与历史身份。

跳转页不复制旧结论，也不作为另一份当前知识收录。工具不引入专用 ID 链接解析器，只改写解析出来的链接，不做全仓字符串替换。实际覆盖见[配置与规则](../../scripts/wiki/reference.md#归档先预览再执行)。

## 检索与检查范围

根 `.ignore` 中的 `/archive/` 让普通 `rg` 默认减少历史结果，归档仍由 Git 保存。按任务需要可以定向读取归档文件，或显式扩大搜索：

```bash
rg --no-ignore '关键词' archive/
```

GNU `grep`、`git grep` 和其他宿主搜索可能使用不同的忽略规则，应按其能力设置默认范围。该设置不构成历史访问限制。

接入旧仓库时，先登记实际的历史根，再配置过渡搜索范围；不要把所有名为 `archive` 的源码目录一律排除。全量生命周期和链接检查独立于搜索忽略规则，仍需检查历史结构。
